**Baseline every gain is quoted against.** M1 §5: a 115 ms step at 31K context (weight GEMMs 81.7 ms at 215 GB/s, verify attention 11.5, drafter 10.4, small kernels 3.9, commit 3.4, GPU idle 3.4, DeltaNet recurrence and conv 2.1), 5.2 accepted tokens per step, ~45 tokens/s on the sampled agent replay; production is 105.5 ms. **Every gain below is an estimate from the sources, not a measurement.** Where sources disagree, the table gives each source's number and then the range adopted. Only a measured win moves from this file into the SPEC's plan.

## The ranked backlog

**Ranking rule.** Expected gain on Mightling's agent workload divided by cost (S under a week, M 1–3 weeks, L longer or needs training). Correctness and client-blocking bugs rank by severity, since their cost is small and their absence blocks production. Items that are not exact against the served checkpoint keep their gain in the ranking but are bucketed as decisions (section 5). Items not pursued are listed in section 6, not here.

**Exactness classes:**
- **exact**: greedy output identical to plain decoding, sampled distribution unchanged, bit-identical to the current path;
- **drafter-only**: acceptance may move, output never;
- **rounding**: floating-point order changes but stays deterministic per row; bit-identity is re-established with `--spec-check` / `--prefix-check` / `ling-stream-tests`, and speculative output still equals plain decoding;
- **not exact**: changes the target's numerics against the served checkpoint; needs the quality gate (B17) and a decision;
- **n/a**: a test, a correctness fix or an API change.

## 1. What M3 should absorb now

For the M3 owner. These are inside M3's stated scope (one graph per step, PDL, the verify-attention kernel); the plan is unchanged.

**B07, the verify-attention kernel.**
- All 16 rows × 6 query heads (96 rows) of one KV head in one CTA, so the KV is read once per step (R§3.4; R7, PAT).
- A split of ≥ 12 ways over the keys, so 4 KV heads fill 48 SMs. The split boundaries are a function of the key position only, never of the row count or of how decode and verify round the context, so M = 1 and M = 16 stay `memcmp`-identical.
- Partials merged in a fixed order through global memory that stays in L2 (~4.7 MB per layer), with the merge fused into the kernel (the last CTA per head reduces). Not through DSMEM: on sm_120, remote DSMEM stores run ~10× slower than on H100 (R30, CREDIT), and a DSMEM reduction elsewhere on GB10 was exact but 2.73× slower (G§5).
- Prefetch deep enough to hide ~1,000 cycles of DRAM latency (M0's ~400 ns): 3–4 `cp.async` stages or bulk copies, not double buffering (H1's latency model).
- 16-byte loads with an evict-first hint; on GB10 sub-word loads are slower than F32 (H1).
- **An ancestor bitmask per row from day one**, so M4's trees do not reopen the kernel (R§3.3, R§3.4); each KV tile loaded once for every node (S§16.10).
- Benchmark on random KV: M1 found all-zero data reads 20% faster.
- Gates from the sources: ≥ 230–240 GB/s at 31K with 16 rows (≤ 8.5 ms per step), ≥ 230 GB/s at 64 rows with a tree mask. References for the split: flash-attention #2336 (SM120 split-KV, validated on SM121a), llama.cpp #30190 (verify tokens and GQA heads packed into one row tile at our shape, 24 Q / 4 KV heads, D 256).

**B08, the graph per step.**
- The per-replay input is raw state copied into fixed buffers; captured kernels derive the rest: the DeltaNet commit plan, the drafter's context-window start and the attention range count come from the accepted count on the device (H3).
- The accept decision runs on the device, so draft, verify and accept are one on-device schedule (L3).
- The drafter's small kernels and the β/α projections fan out on a second stream captured in the same graph (H3).
- `CUDA_MODULE_LOADING=EAGER`, or a warm-up before serving, so lazy module loading does not land in the first request (H3).
- PDL: run `compute-sanitizer --tool racecheck` and the bit-identity suites with PDL on; llama.cpp found and removed a PDL race on DGX Spark (#23825). PDL pays most on small-grid kernels (TRT-LLM #18714).
- A graph-replay stress test: 10,000 steps with random accept counts (0–15) and context growing across the 4,096-key range boundaries; tokens and DeltaNet state compared with an eager run. A GB10 forum report of intermittent token corruption with MTP plus CUDA graphs is the case it guards (H3).
- Measure first and after (L2): GPU idle per step, the small-kernel total and the bubble at each layer boundary, from an Nsight Systems trace of 60 steps at 31K (`bench/profile/step_breakdown.py`). Gate: idle ≤ 1 ms, as production has. The boundary bubble is B32's input.

**Seen and left out of M3:** the drafter head (B25), GDN glue fusion (B35), recurrence tuning (B28, which goes with M4's kernel change) and FP8 KV (B41, a decision).

## 2. Inputs to the M4 tree-verification plan

**Expected gain:** +5–12% decode (B11), +1–3% more under sampling from B09, −0.3 to −1 ms from B28.

**Before building (queue slot 4, ~4 h):**
1. **The verify cost curve:** one pass at 16, 24, 32, 48 and 64 chain rows at 31K, 50 passes each (R§3.3(a); G1's width gate: step growth ≤ 5 ms at 32 rows; M1 measured 12 → 16 rows at +2.8 ms).
2. **Shadow ranks**, from B10's log: the share of rejections whose target token is the selector's 2nd–4th candidate given the accepted predecessor.
3. **Exact offline acceptance** for greedy trees of 16, 24, 32 and 48 nodes on the tuning set, each root-to-leaf path verified as its own chain with today's kernels (R§3.3(c)), scored with R17's estimator.
4. **Go** if trees add ≥ +10% accepted tokens at a budget ≤ 32 (G1) and CAST's rule applied to step 1's curve predicts ≥ +5% decode (R§3.3). Otherwise trees wait for the drafter work (B30) to raise the chain.

**How to build the tree:**
- From the selector's 16×16 transition scores, not from the per-position marginals. On a drafter with a transition head, marginal-only trees lost to the chain: τ 2.60–2.72 against 4.39 (TreeSpark).
- A best-first heap over lattice paths keyed by the product of `softmax(score[e][prev])`.
- Width by CAST's rule: add a node while its path probability exceeds (current tokens per ms) × (ms per extra verify row), about 5.2 / 115 = 0.045 tokens per ms today.
- A fixed shape (DARTree) so the captured graph stays static; the fixed shape costs about 6% of the tree's gain.

**Verification rules:**
- **Greedy:** a deterministic tree with target-sample matching; no exact verifier beats 1 + target coverage (R18, TEV).
- **Sampled:** siblings drawn without replacement from the selector's tempered distribution and checked with traversal verification (Tsubame, proved exact). **Never** a deterministic top-k tree with rejection sampling: it is biased (TV 0.46) and measured −1.5% on DFlash2 (R§4).
- B09's block verification is the chain case of the same rule and lands first.
- Ties break to the lower token id everywhere, the selector's top-16 included (S§18).

**DeltaNet side:**
- Parent indices in the verify (FlashInfer #6155's `verify_parents`). Chain parents must stay bit-identical to today's chain path.
- Step 1 is a path recompute from S₀ (estimate +2–3 ms for 16 nodes with ~4 leaves); the TreeWY or Bole closed form only if that cost matters (S§16.6). The conv window follows parent pointers.
- No per-branch state forks: a fork cost +7.40 ms each on GB10 in another engine (G1).
- The commit replays only the accepted path. FlashInfer #6257's warning applies: a commit that replays rows by loop counter takes the rejected row into the checkpoint.
- B28's recurrence tuning goes in while the kernel is open; B29's fold comes after, designed for path commits.

**Attention side:** B07's ancestor bitmask, with each KV tile loaded once for all nodes.

**Interface:** B36. A proposer returns nodes with parent indices and per-node q, so the lookup branch (only if B44 passes) and a diffusion-style generator (L11) fit without a second verify path.

**Exactness tests:**
- `--spec-check` with trees on, every bucket;
- chi-square for traversal verification;
- the state after a partial accept bit-identical to a plain run;
- B08's stress test extended to random tree shapes.

**End-to-end gate** (~2 h): the main replay set, sampled. Decode ≥ +8% at equal exactness checks (G1).

**Probes that ride on the same log:**
- carryover's re-convergence (≥ 2 positions per rejected round decides whether B30 includes it);
- exit mass (R18);
- acceptance per position and against context (B10).

Draft width per concurrency waits for batching (B31).

## 5. Decisions needed from the maintainer

1. **FP8 KV (B41).**
   - Gain: −3.5 to −5 ms per step at 31K, more past 64K.
   - Exactness: not exact against BF16 KV. Speculative output still equals plain decoding at the same cache precision.
   - Gate: B17's tool-call replay and long-output stress, not perplexity.
2. **4-bit KV at 64K–128K (L6).**
   - The evidence against it: NVFP4 KV lost 29% of decode on GB10 (G§5), q4_0 KV lost 37% at 110K, and users report tool-call damage (H§4).
   - The question: run the measurement at all, beside FP8, or close it?
3. **All-NVFP4 projections (B12).**
   - Gain: ~−12 to −15 ms per step, the largest single step lever listed.
   - Exactness: not exact against the served checkpoint.
   - Gate: the quality gate on the published all-NVFP4 checkpoint first.
4. **Ternary weights (B45).**
   - Target: a different model, not exact. No ternary checkpoint of Qwen3.8-27B is cited by any source.
   - Drafter: drafter-only.
   - The question: evaluate at all, and if so drafter first.
5. **CPU placement on the production machine (B40).**
   - Pinning ling-serve's step thread to a fast core shares the host with SWE-bench containers, indexers and the web UI.
   - Related: S§16.9's proposal that Mightling's admission count memory bandwidth, not only memory.
6. **GPU clock cap.**
   - G§5 cites a 2,000 MHz cap costing 2.7% of decode for 49% less GPU rail power.
   - This trades speed for energy per token (L1). Production behaviour, so the maintainer's call.
7. **The fine-tuned drafter's reach (B30).**
   - Fine-tuning is allowed on the development GB10 only, and its logs and weights never leave that machine.
   - A drafter trained there therefore cannot serve production on another machine.
   - The question: keep it as a measurement on the development GB10 only, or allow the weights (not the logs) onto the production machine.
8. **FP16-accumulate MMAs.** Only if slot 1 shows GB10 halving FP32-accumulate HMMA. Using them in prefill attention changes numerics (G's "considered").
9. **BF16 prefill intermediates (B34).** Production keeps them in BF16; ling-serve keeps FP32. Moving to BF16 changes ling-serve's prefill numerics.
10. **Per-GPU kernel-variant tables (B42).** Either restrict the search to variants with identical arithmetic order (recommended: every GB10 then gives the same greedy output), or accept greedy output that differs between machines.
11. **NVMe spill of cold sessions (B43).** It writes conversation content to disk. Exact, but it stores session data where none is stored today.
12. **The A/B.**
    - The pass criterion: resolved count on the 24-instance sample against production's, and with what margin. Plus any limits on first-token latency or tool-call failures.
    - Whether ling-serve may replace SGLang before batching (B31). Two SWE-bench sessions would run one after the other.
13. **Production-side checks.** Running the concurrency-8 greedy test (G§6) against production's own SGLang image touches production.
14. **Codex Code Mode (B49).** Render custom tools in ling-serve, or keep Code Mode out of the launcher's catalog. Decide with the launcher.
15. **Stop strings inside the reasoning and tool calls written before `</think>`** (S§18, B46). Follow production's behaviour, or fix them. The second only after B46's rate is known.
