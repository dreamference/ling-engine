# Microbenchmarks of spec §16.1, re-run with the reference server resident

October 10, 2026 · measured on the development GB10 (`second-puffin`), with M0's reference container (`m0-prod8000`: SGLang, 16 draft tokens, `--mem-fraction-static 0.6`, 262,144-token context, serving port 8000) **resident throughout**. It was idle during items 1–3 and driven by the measurement during item 4. Nothing was stopped or restarted.

M0 ([M0.md](M0.md) §1–2, October 8) made these five measurements on an idle machine. This run repeats them in the condition the engine will actually meet when it is measured beside production, with the toolkit the tree builds with today, and adds the one probe M0 asserted rather than compiled (the sm_100 tensor-memory path). The research spec's §16.1 now carries one "Measured 2026-10-10" line per item; M0's numbers stay the idle-machine reference.

## Summary

1. **Latency is unchanged with the server resident:** 395–402 ns to DRAM, 136 ns in L2. At the measured 257 GB/s that is ~103 KB in flight across the chip, ~2.1 KB per SM (M0: 105 KB, 2.2 KB).
2. **The bus delivers 257–259 GB/s** (94–95% of 273) to a read stream with the reference server resident but idle, against M0's 262–264 on a bare GPU: the resident server costs ~2%, not the 9% M0's SM-scaling run saw (238 GB/s). **8 SMs reach 99% of the 48-SM figure, 4 SMs 96%.** Item 2's conclusion stands: a weight stream needs few SMs; the rest of the chip is free for other work.
3. **sm_121 under CUDA 13.0.88 exposes everything the kernels assume** (block-scaled NVFP4 and FP8 `mma.sync`, TMA, clusters of up to 8 blocks with DSMEM, PDL), and **refuses `tcgen05`**: ptxas rejects `tcgen05.alloc` for `sm_121a` and accepts the same file for `sm_100a`. The `-arch=sm_121a` trap (compute_121 PTX) still reproduces.
4. **Ten minutes of two-stream decode on the reference server: no throttling.** SM clock 2,405–2,476 MHz (median 2,431), power median 44 W, peak 45 W, temperature peak 69 °C, throttle-reason mask 0x0 in all 709 samples; 34.7 tokens/s per stream at concurrency 2 (M0: 33.9).
5. **The acceptance histogram** was not re-measured: it needs ling-serve's model loaded beside the resident reference server, which the project has never done (M3 stopped the reference for clean memory). M0 §4 and M1 §4 hold it at 16 draft tokens; a 12-draft histogram on the tuning set remains open.

The tree at `15f73f3` builds (ninja, ccache-warm: 12 s), and `ling-kernel-tests`, `ling-stream-tests`, `ling-sampling-tests` and `ling-api-tests` pass (the API tests report their 2 known gaps, [engine-issues-2026-10-09.md](engine-issues-2026-10-09.md)).

## 1. Latency and bytes in flight (§16.1 item 1)

`latency`, a single thread following a cyclic permutation of 128-byte lines (`ld.cg`), lines spread over the whole buffer or confined to 64 KB windows:

| Buffer | Random lines | 64 KB windows | M0 (idle) |
| --- | --- | --- | --- |
| 1–8 MB (L2) | 136.4 ns | 136.4–136.6 ns | 141–143 |
| 16 MB | 190.2 ns | 188.0 ns | — |
| 64 MB | 395.2 ns | 393.4 ns | 398 |
| 256 MB–1 GB (DRAM) | 401.7–401.8 ns | 397.4 ns | 401–403 |

The resident server's pinned memory does not change the load-to-use latency. At 257 GB/s × 400 ns, a stream needs ~103 KB in flight across the chip, **~2.1 KB per SM on 48 SMs**, 13 KB per SM if 8 SMs do the streaming. The pipeline depth of §9's kernels is sized from this number.

## 2. How many SMs saturate the bus (§16.1 item 2)

The read-only stream of `membw.cu` over 8 GiB, confined to k SMs (the kernel records which SM ran each block), best of 3:

| SMs | 4 | 8 | 12 | 16 | 20 | 24 | 32 | 40 | 48 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| GB/s, one 1024-thread block per SM | 248.3 | 256.6 | 257.2 | 257.9 | 257.8 | 258.3 | 255.2 | 256.7 | 255.1 |
| GB/s, two blocks per SM | 256.6 | 258.1 | 258.2 | 252.9 | 257.8 | 257.0 | 248.1 | 258.2 | 258.9 |
| M0 (idle, one block per SM) | 235.6 | 241.4 | 241.2 | 240.6 | — | 240.3 | 239.5 | — | 238.2 |

(M0's SM-scaling row was its one measurement with SGLang resident; its bare-GPU peak was 262.8.) Four SMs with one block each reach 96% of the 48-SM figure and eight SMs 99%; with two blocks per SM, four SMs already reach it. The two dips (32 SMs one block, 16 and 32 SMs two blocks: 32 and 64 blocks) are reproducible in both runs and sit on the same block counts, so they are a placement effect of the block scheduler rather than noise. **A weight stream needs 8 SMs; the remaining 40 are free** for the DeltaNet scan, attention, sampling (§16.6–16.7), and wave quantization of weight-streaming GEMMs (§16.8) costs no bandwidth.

The full `membw` sweep in the same state, for the record against M0 §1:

| Measurement | GB/s | M0 (idle) |
| --- | --- | --- |
| Read-only stream, best of the sweep (`ldg`, 4 × 16 B per thread, 192 blocks × 1024) | 258.1 (94.6% of 273) | 262.8 |
| Sustained 15 s, median (min / max) | 257.0 (256.9 / 257.2) | 261.1 (259.2 / 261.8) |
| Simplest kernel (1 block of 256 per SM, no unroll) | 248.9 | 251.9 |
| Read sizes 64 MB … 8 GB (median of 9) | 243.8 … 257.4 | 260.0–263.7 |
| Write-only | 195.9 | 194.8 |
| Copy, kernel (read + write bytes) | 225.3 | 226.9 |
| `cudaMemcpy` device to device (read + write bytes) | 243.7 | 155.1 |
| `cudaMallocManaged`, preferred location GPU | 161.4 | 164.3 |
| `malloc`, CPU first touch | 168.8 | 167.4 |

Two differences from M0: the read stream is 2% lower everywhere (the resident server's share of the bus, visible even idle), and small buffers (64 MB–1 GB) read 5–7% slower than 8 GB where M0 saw a flat curve. The device-to-device `cudaMemcpy` figure is 243.7 against M0's 155.1; the cause was not investigated (it is not a path the engine uses).

## 3. What sm_121 exposes (§16.1 item 3)

`isa_probe` under CUDA 13.0.88, each feature run on the device and its result checked:

| Feature | Result |
| --- | --- |
| Block-scaled NVFP4 `mma.sync.aligned.kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64` (E2M1, UE4M3 scales) | works, d = 64 = K |
| FP8 `mma.sync.aligned.kind::f8f6f4.m16n8k32` (E4M3 × E4M3) | works, d = 32 = K |
| TMA: 2-D `cp.async.bulk.tensor` with an mbarrier | works |
| Thread-block clusters with distributed shared memory | works; largest cluster launched: **8** blocks (12 active clusters of 8, 24 of 4, 48 of 2) |
| Programmatic dependent launch | works: the secondary's prologue ran 199.6 µs before the primary ended (the primary is a ~200 µs spin: it starts as soon as the primary is scheduled) |
| Shared memory | 99 KB per block (opt-in), 100 KB per SM; 64K registers per SM; L2 25.2 MB |
| `tcgen05.alloc.cta_group::1` / `tcgen05.relinquish_alloc_permit` (`tcgen05_probe.cu`) | **refused**: ptxas "Instruction 'tcgen05.alloc' not supported on .target 'sm_121a'", also for `.cta_group::1`; the same file compiles for `sm_100a` |

So TMEM, the 5th-generation MMA and 2-SM MMA are absent on sm_121, as §16.1 and §16.13 expected; this is now a compiled result, not an assumption. The toolchain trap holds: `nvcc -arch=sm_121a` emits `compute_121` PTX and ptxas rejects `.kind::mxf4nvf4`, `.block_scale`, `.scale_vec::4X` and `.kind::f8f6f4` for it; `-gencode arch=compute_121a,code=sm_121a` is required (as `CMakeLists.txt` sets).

## 4. Clocks, power and temperature across a 10-minute decode (§16.1 item 4)

`decode_clocks.py` against the reference server: two concurrent streams of back-to-back `/v1/chat/completions` requests (4,096 max tokens each, thinking off, production's sampling: temperature 1.0, top-p 0.95), for 600 s plus the last requests' tail, while `nvidia-smi --query-gpu` sampled once a second. `clocks.mem` is `[N/A]` on GB10; the throttle-reason mask is reported.

| Column (709 one-second samples) | min | median | max | M0 (10-minute replays) |
| --- | --- | --- | --- | --- |
| SM clock, MHz | 2,405 | 2,431 | 2,476 | held 2,405, min 2,372 |
| Power, W | 12 (before the first request) | 44 | 45 | median 42–54, peak 82 |
| Temperature, °C | 45 | 68 | 69 | peak 79 |
| GPU utilization, % | 0 (before the first request) | 96 | 96 | — |
| Throttle-reason mask | 0x0 in all 709 samples | | | not logged |

12 requests, none failed, every one ran to its 4,096-token cap: 49,152 completion tokens in 709 s, 69.3 tokens/s in all, 34.7 per stream (per request: 29.9–40.4, median 35.7), against M0's 33.9 per stream at concurrency 2.

**No throttling in ten minutes of decode.** The SM clock never fell below its 2,405 MHz base and spent the run between 2,405 and the 2,476 MHz boost (the device reports 2,418 as its maximum; the boost above it is real and sustained); the driver raised no throttle reason at any second. Power sat at 44–45 W and temperature at 68–69 °C, both below M0's replays (82 W peak, 79 °C), which carried 25K-token prompts and so a prefill share this run has not: a pure decode is a cool, weight-streaming workload at a third of the 140 W budget. §16.9's concern, that compute- and memory-heavy phases need interleaving to stay out of throttling, does not arise at this load; the prefill-heavy case remains to be measured.

The prefill-heavy case (a long prefill rather than a long decode) was not run, as in M0.

## 5. The acceptance histogram (§16.1 item 5)

Not re-measured. It is read from ling-serve's `GET /spec_stats` over a replay of the tuning set, which needs the model (17.6 GB of weights, the drafter, the KV and state buffers) loaded beside the reference server's 83 GB of pinned memory, on a machine with 38 GB available. The project's measurements of ling-serve have always stopped the reference server first (M3), and a few ad-hoc prompts would not be comparable with M0's 1,295-step histogram anyway. The measured histogram stands as M0 §4 reports it, at 16 draft tokens: ceiling bin 3.6%, 43% of steps accepting 0–2 drafted tokens; M1 §4 measured ling-serve's own at the same block (ceiling 3.6%, 14.1% at 0). Production and ling-serve run 12 draft tokens since 2026-10-09; the 12-draft histogram on the tuning set is a replay for a GPU without the reference server.

## Not a measurement: "BF16 intermediates"

The note that mentions BF16 intermediates is backlog item B34 ([backlog-2026-10-09.md](backlog-2026-10-09.md) §B34 and its open question 9; [M2-prefill.md](M2-prefill.md) §8 item 3; MILESTONES §14): the prefill's conv, norms and gates move FP32 tensors (~15% of a 35K-token prefill) where production keeps BF16, and the milestone text allows the BF16 path to be built behind a switch. It is a code change with a numerics consequence and its own agreement check, not a microbenchmark, and nothing in `specs/` or `reports/` defines a measurement by that name. It was not built or measured here.

## How to run

```bash
bench/micro/build.sh
build/micro/isa_probe
build/micro/latency
build/micro/membw 8 15
nvcc -std=c++20 -gencode arch=compute_121a,code=sm_121a -c bench/micro/tcgen05_probe.cu -o /dev/null   # expected to fail
python3 bench/micro/decode_clocks.py --url http://127.0.0.1:8000 --duration 600 --streams 2 --max-tokens 4096 --csv /tmp/clocks.csv
```
