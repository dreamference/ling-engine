# Images in ling-engine: what was built and measured, 2026-10-26/27

Branch `vision/image-input` ([VISION §20](../specs/DREAMFERENCE_LING_ENGINE_VISION.md)): Qwen3.8-27B's vision tower on the GPU, image tokens in the prefill with M-RoPE positions, `data:` URLs through the chat and Responses APIs, and the image-input gates of §20.5. Windows 1–3 and 5 ran on node-b; 6–10 on node-c, a third GB10, after node-b's GPU went to the concurrency work.

## 1. Decode, preprocessing and rendering (windows 1–2)

- Decode: 0 values differ from production's on all 14 test images, including 6 JPEGs through nvJPEG.
- Resize: at most one level apart, on 0–0.008% of values.
- Rendering: 24/24 prompts token-identical to production's prompt ids.

All the measurements in this report used an earlier rendering of `bench/vision/images/terminal.png`; the committed file was re-rendered afterwards with a neutral user name and path, the same layout and size.

## 2. The tower (phase (a))

Measured against transformers' FP32 tower (no TF32) on 14 images:

- **Against transformers BF16:** the engine has the lower relative L2 on 14/14 (small images 1.1–3.5e-2 against 1.6–4.6e-2; 4K-token images 2.9–6.0e-2 against 7.3–11.7e-2; 12–16K-token images about 5e-2 against 0.20–0.24).
- **Against production's own tower** (SGLang v0.5.21, window 6): at par. The geometric mean of the L2 ratio is 0.993.
  - L2: the engine is worse on 8 images, by 0.6–12% (code: 5.70e-2 against 5.08e-2), and better on 6, by up to 9%.
  - Cosine p1 and median are equal within 0.001.
  - Worst token's cosine: worse on 6 (code 0.890 against 0.946), better on 8.
  - This passes the production-floor rule of §20.5 item 3, a technical default of 2026-10-27. The code screenshot's worst token is BACKLOG 36.
- **Speed:**
  - 0.11–0.33 s at 0.5–1.4K tokens.
  - 5.6–5.9 s at 4K tokens.
  - 12.6 s and 21.2 s at 12K and 16K tokens.
- **Memory**, as allocated at start: tower 881 MB, scratch 1,098 MB at 65,536 patches, embedding cache 512 MB.

## 3. Exactness (phases (b) and (c))

**Image prompts:** `--spec-check`, `--prefix-check`, `--graph-check`, `--batch-check` and `--chunk-check 256` pass on all 24 image prompts. Resuming inside an image also passes: an 8K-token image resumed at 4,096, with the state, the next token and the continuation identical to a prefill from scratch.

**Text** (window 4, node-b), against main `c5ec4ec`:
- Every test binary exits 0.
- `--spec/batch/graph/prefix-check` pass.
- Agentlong greedy: 16/16 turns identical, 781 verify passes in both (decode 78.07 against 77.17 s).

**The chunk-check failure of window 3** (image prompt 4: 12 steps and 58 accepted against 11 and 59) was a main bug, not an image one.
- **Cause:** a prefill chunk of 32 rows or fewer took the drafter's NVFP4 fc, and a larger one the BF16 GEMM.
- **Evidence:**
  - With the drafter ring hashed, the build without the fix differs on 5/24 image prompts and 4/32 padded text prompts; the fixed build differs on 0 of each.
  - Main shows it on text: 1/32 continuations differ.
- **Fix:** merged into main separately as `c6c1cc9` (BACKLOG 33).

## 4. End to end (phase (d))

**Agreement**, teacher-forced on production's greedy continuation, 1,074 positions over 24 prompts (windows 2 and 6, the same numbers):

| | Engine | Production's own decode against its prefill | Result |
| --- | --- | --- | --- |
| Flips | 53 (4.93%) | 60 (5.59%) | Fisher p = 0.78 |
| Worst flip gap | 6.6 nats | 10.6 nats | pass |
| Outside top-5 | 1 | 2 | pass |

Free-running greedy output is identical to production's on 7 of 24 prompts.

**Cold time to first token**, ling-serve against production, the same 24 prompts in the same order (window 6, node-c; production's from window 1, node-b):

| | ling-serve | Production |
| --- | --- | --- |
| Whole set | 56.5 s | 135.8 s |
| 4K-token images (8.2K-token prompts) | 7.8–8.3 s | 18.2–20.1 s |
| 3-image prompt (11K tokens) | 4.7 s | 23.9 s |
| Small prompts, together | 12.0 s | 15.2 s |

- 4K-token images: 2.3–2.6 times faster.
- 3-image prompt: 5.1 times faster, partly from images already in the embedding cache.
- Small prompts: from 0.4 to 3.0 times production's speed per prompt.

**HTTP tests:** `tests/server` against ling-serve with images on: 69 passed, 3 xfailed (window 7, and the merged tree in window 10). In window 9 the merged tree failed one test twice out of two full runs, `test_two_requests_run_at_once_and_each_equals_alone`, on its timing line only (the second request's first token came 0.06 s after the first request ended). Main `c6c1cc9` has the same race: run alone 15 s apart, it failed 2 of 4 runs on main and 1 of 4 on the merged tree; in one full run each, both passed it. Both builds fail it when the second request's prefill beside a decode takes 1.28 s and pass when it takes 1.60 s, because the first request's 160 tokens decode in about 1.3 s. This is a defect of the test's margin, not of the images.

## 5. The merge

Main (`e1eac84`, admission control) was merged into the branch. ling-serve's start-up memory plan now counts the tower's scratch and the embedding cache when images are on. Windows 8–10 gated the merged tree (the same code as the branch's tip) on node-c:

- **Window 8:** all 11 test binaries exit 0. `--spec/batch/graph/prefix/interleave-check` pass on text. On the 24 image prompts, `--spec-check` passes, and `--chunk-check 256` passes with the drafter context identical on 24/24. `chunk-long` passes 7/7, with prompts of up to 30,950 tokens.
- **Window 9:** agentlong greedy against main `c6c1cc9`: 16/16 turns identical, 5,271 tokens, 781 verify passes in both (decode 80.86 s against 80.91 s).
- **Window 10:** the HTTP tests above, against main and against the merged tree.

## 6. Open

- Mightling's ling-serve image needs libpng16-16t64, libwebp7 and libjpeg-turbo8. libnvjpeg is optional, with libjpeg-turbo as the fallback.
- `usage.prompt_tokens_details.image_tokens` is not reported.
- BACKLOG 36: the code screenshot's worst token.
- `test_two_requests_run_at_once_and_each_equals_alone` needs a wider margin, for example a longer first answer, so that its overlap line does not race the prefill beside a decode.
