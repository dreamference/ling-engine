# M1: speculation

October 9, 2026 · measured on the development GB10 (`second-puffin`), against M0's measurements of production on the same machine ([M0.md](M0.md)). Recorded sessions are replayed locally and never leave it; only aggregates are reported.

## Summary

1. **Speculation works and is exact.** ling-engine now drafts with the DFlash2 drafter production serves and verifies a 16-token block in one target pass.
   - **Greedy:** output is token for token identical to plain decoding. The recurrent state after a speculative run is bit for bit the state of a plain run over the same tokens.
   - **Sampling:** exact rejection sampling, checked by chi-square.
2. **On M0's main set** (12 replayed agent sessions × 12 requests, single stream, production sampling) the engine decodes at **45.5 tokens/s**: **5.21 tokens per step at a 114.5 ms step**.
   - **Against production:** 47.1 tokens/s, 4.95 per step, 105.5 ms. That is **97% of production's decode speed** with 5% higher acceptance and an 8.6% longer step.
   - **Against tuned SGLang** (12 draft tokens): 48.5, so −6%.
   - **The trend:** the first M1 build measured 33.7 tokens/s at a 146 ms step on the same set.
   - **On M0's tuning set** the engine matches production: 49.8 against 49.1.
3. **The verify's weight GEMMs already beat production's.** The target's 17.6 GB stream in ~82 ms against 86.3 ms. Two things did it:
   - tensor-core streaming kernels over weights retiled at load into the order the kernel reads them;
   - one launch per group of matrices that share an input.

   The rest of the step is where the gap is: attention (~9 ms against 6.1 at 24K), the drafter's pass over the 0.72 GB head, and ~8 ms of small kernels and launch gaps (section 5).
4. **A wider verify is nearly free here.** Block 12 shortens the step by only 2.8 ms but loses 10% of acceptance (45.8 against 49.8 tokens/s on the tuning set), so the engine keeps 16 draft rows. Production's SGLang gains from 12; the engine does not.
5. **The context lookup does not pay on this workload.** Scored in shadow on every step, it loses to the drafter in every match-length bucket (even 32+-token verbatim copies: 6.9 against 9.9 accepted). The best of both per step is only +4%. The spec's simulated ×1.2 assumed independent successes (section 6).
6. **Per-request latency is not yet production's.** Warm time to first token is 1.7 s against 0.31 s, because v0's prefill dequantizes every weight per chunk. A request takes 8.1 s on average against 4.2. Decode parity does not reach the agent until prefill is replaced (lever 3).
7. **Accuracy against production is unchanged.** Greedy tokens agree with production SGLang's top-1 98.6% of the time and its top-5 always (v0: 97.6% and 100%).

## 1. What was built

| Part | What it does |
| --- | --- |
| `stream_gemm.cu` | Weight streaming on tensor cores for 1–32 rows: NVFP4 (E2M1 values and E4M3 block scales converted to FP16 in registers, exactly) and FP8 weights, activations in FP16 with a power-of-two scale per row, FP32 accumulation, `mma.sync.m16n8k16`. Split-K chosen from the matrix shape. |
| The rows path | Every pass of 32 rows or fewer (decode, verify, short prompts) goes through `stream_gemm`, a narrow BF16 kernel for the DeltaNet β/α projections, and tensor-core attention over fixed 512-key ranges. Every kernel on it is row-invariant: a row's result is bit for bit the same whatever the other rows are. |
| The DFlash2 drafter | `maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal`, run as SGLang's DFLASH path runs it (section 2). |
| Verify and commit | A verify writes the rows' KV but leaves the DeltaNet and conv state as it was, keeping each layer's inputs; the commit replays the accepted rows through the same kernels. |
| Acceptance | Greedy (a draft survives while it equals the target's argmax), or exact rejection sampling against the selector's 16-way draft distribution (`accept.cpp`). Requests with presence or repetition penalties decode without speculation, since their penalties are applied over the full vocabulary. |
| Context lookup | `lookup.cpp`: the continuation of the most recent earlier occurrence of the last 3 tokens. *Shadow* mode scores it against what was generated; *auto* mode verifies it in place of the drafter's chain on a long match. |
| Server | `ling-serve --draft DIR [--draft-block N] [--lookup 0/1/2]`; `/metrics` under SGLang's counter names, so M0's replay harness runs unchanged; `/spec_stats` for the acceptance histogram and lookup scores. |

## 2. The drafter, as production runs it

The drafter is `maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal`, the one production serves (1.55 GB). The engine runs it as SGLang's DFLASH path does (`models/dflash.py`, `speculative/dflash_worker_v2.py`, read from the 0.5.21 source):

- **Its context.** The target's residual stream after layers 5, 19, 33, 47 and 61 (SGLang captures it at the input of the next layer) is kept in BF16 for every committed token. `fc` and a plain RMSNorm turn the five features into one 5120-wide vector. Each of the five drafter layers projects it straight to its K and V, with no input norm and no convolution, then applies its k-norm and RoPE (θ = 10⁷, full 128 dimensions) at the token's position. A prompt contributes only its last 2048 positions, the drafter's sliding window.
- **The block.** `[anchor, mask × (B − 1)]` (mask id 248070), embedded with the target's table, at positions pos … pos + B − 1. Attention is bidirectional inside the block (the checkpoint says `is_causal: false`) and reaches back 2047 positions into the context. Each sublayer is wrapped in DFlash2's two-tap grouped convolution: a coefficient projection, plus a base kernel, with the second tap masked at block position 0. The drafter's norms are plain (`x · w`), not the target's `(1 + w)`.
- **Candidates and path.** The drafter's final hidden states for positions 1 … B − 1 go through the *target's* NVFP4 LM head, then the top 16 per position. The candidate selector scores the 16 × 16 transitions between adjacent positions, `unary + ⟨pred[prev] ∘ proj(h), succ[cand]⟩`, with the anchor as the first position's predecessor. One path is then walked: the argmax (ties to the lower index) when greedy, or a draw at the request's temperature when sampling. That draw's 16-way distribution is the draft's q for rejection sampling.
- **The verify.** A chain of B rows, as in production (M0 §7).

On the replay this reproduces production's acceptance: **4.98 tokens per step against 4.95** (section 4).

## 3. Exactness

Three checks, all passing on the final build:

1. **Greedy output is identical to plain decoding, token for token.** `ling-run --spec-check` decodes each prompt plainly, then speculatively. It compares the tokens. It then replays the speculative run's tokens through plain decoding and compares every DeltaNet and conv state bit for bit (spec §13).
   - Coverage: code, prose, JSON, arithmetic, and an 11,447-token prompt through chunked prefill; verify blocks of 8, 16 and 32; 200 tokens each.
   - Every run: tokens identical, state identical.

   Two design rules make this hold:
   - **Row invariance.** Every kernel on the rows path computes a row bit for bit the same whatever the other rows are: `stream_gemm` (fixed K-chunk order per warp, a fixed-order warp reduction, split-K never chosen from M), the narrow BF16 kernel, and attention over fixed 512-key ranges at fixed positions, where a tile past a row's last key leaves its online-softmax state exactly unchanged. Plain decode (M = 1) and a verify (M = B) therefore run the same arithmetic per token. `ling-stream-tests` asserts it for every kernel with `memcmp`.
   - **Commit by replay.** A verify reads the DeltaNet state and does not write it. It keeps each layer's projected inputs before and after the conv, the decay and the write strength. The commit replays the accepted rows through the same conv and recurrence kernels, whose per-token arithmetic does not depend on how many tokens one call covers.
2. **Sampling is exact.** Rejection sampling (`accept.cpp`): a draft is accepted with probability min(1, p/q), a rejection draws from max(0, p − q) normalized, and the target's p is the same truncated chain as plain sampling (temperature, top-k, top-p, min-p). `ling-spec-tests` runs a toy model (position-dependent target distributions with impossible tokens, random draft distributions, and deterministic lookup proposals) through 300,000 speculative decodes per case. It compares the joint distribution of the first three tokens with the target's by chi-square; all four cases pass the 99.9% bound and no impossible sequence is ever emitted. Requests with presence or repetition penalties decode plainly: their penalties act on the full vocabulary, and the accept step sees each row's top-K.
3. **The API.** `bench/serve_smoke.py` passes against `ling-serve --draft` (chat, reasoning split, streaming, typed tool calls, completions from ids).

## 4. Speed on replayed agent sessions

Method: M0's replay harness and session sets, unchanged.
- **Requests:** the real Responses requests, production sampling (temperature 1, top-p 0.95, top-k 20), output capped at the recorded length.
- **Counters:** ling-serve's SGLang-named counters give decode time (end-to-end minus time to first token), verify steps and generated tokens.
- **Conditions:** single stream; the reference SGLang and every other engine stopped for clean memory and timing.
- **Production's numbers** are M0's, on the same machine.

**Main set** (12 sessions × 12 requests):

| --- | --- | --- | --- | --- | --- |
| Production (SGLang, 16 draft tokens; M0, two runs) | 47.1 / 46.8 | 4.96 / 4.94 | 105.5 / 105.4 | 0.31 | 4.2 |
| Tuned SGLang (12 draft tokens; M0, two runs) | 48.5 / 48.2 | 5.24 / 5.22 | 108.2 / 108.4 | — | — |
| ling-engine, first M1 build (`bd2267f`) | 33.7 | 4.92 | 146.0 | 1.72 | 9.4 |
| **ling-engine, M1 (`6db039e`)** | **45.5** | **5.21** | **114.5** | 1.68 | 8.1 |

**Tuning set** (6 sessions × 8 requests), the verify width:

| | Decode tokens/s | Tokens per step | Step (ms) |
| --- | --- | --- | --- |
| Production (M0, three runs) | 48.5 / 49.1 / 49.6 | 5.31 / 5.35 / 5.36 | 109.4 / 108.9 / 108.0 |

| ling-engine, block 16 (`2fb9bbb`) | **49.8** | 5.90 | 118.6 |
| ling-engine, block 12 (`2fb9bbb`) | 45.8 | 5.30 | 115.8 |

- **Acceptance.** The engine runs production's drafter as production does and accepts as much or slightly more: 5.21 against 4.95 on the main set, a 4.92 first run, and 5.90 against 5.35 on the tuning set. Sampled outputs differ run to run, so a few percent is noise. A plausible source of the rest is precision: the engine keeps activations in FP16 (exact NVFP4 and FP8 weights, FP16 inputs), where SGLang quantizes them to FP4 and FP8. The drafter then sees target features closer to the BF16 ones it was trained on. This is unmeasured.
- **Acceptance histogram** (main set, share of steps by accepted drafts 0–15): 14.1, 15.2, 13.7, 10.7, 8.6, 7.6, 6.6, 5.0, 3.1, 2.9, 2.7, 1.9, 1.6, 1.6, 1.1, 3.6%. Production's: 15.8, 15.3, 11.8, 10.6, 8.4, 7.5, 6.5, 5.0, 3.5, 3.2, 2.6, 1.8, 1.8, 1.7, 1.0, 3.6% (M0 §4).
- **The step, host-measured on the main set:** 10.9 ms drafting (block, top-16 candidates, selector), 99.7 ms verify and accept, 3.9 ms commit (DeltaNet replay and the drafter's context KV).
- **How the step came down** (single prompt, greedy, block 16):

  | Build | Change | Short context (ms) | 31K context (ms) |
  | --- | --- | --- | --- |
  | `2827cf2` | first exact build | 126.7 | — |
  | `bd2267f` | β/α projections read once, split attention | 113.4 | 128.8 |
  | `635f1a9` | tiled weights, fused launches, tensor-core attention | ~107 | ~122 |
  | `2fb9bbb` | 4096-key attention ranges, fused norm, streamed drafter BF16 | 104.8 | 116.5 |
  | `6db039e` | head-major KV, warp recurrence | 104.4 | 116.4 |

  The `635f1a9` row is derived: that build ran 5.8% faster than `bd2267f` on the same greedy prompts.
- **Prompt fidelity:** ling-serve renders the replayed Responses requests a median 129 tokens shorter than recorded (SGLang: 0, M0 §3). That is v0's Responses-to-chat conversion; it barely moves a 24K-token context, and it is M4's to fix.
- **Not measured here:** two or four concurrent streams. ling-serve runs one sequence at a time; batching is lever 5.

## 5. Where the step goes

Nsight Systems 2025.3.2, a 30,860-token prompt, 59 speculative steps (block 16), build `2fb9bbb`, `bench/profile/step_breakdown.py`: GPU time per step by kernel family, beside M0's split of production's step (~24k context).

| Part | Engine, 31K context (ms) | Production, ~24K (ms, M0 §5) |
| --- | --- | --- |
| Weight GEMMs, target | ~82 | 86.3 |
| Weight GEMMs, drafter (5 layers, its pass over the 0.72 GB head) | ~7.5 | (in the drafter's 8.6) |
| Attention | 11.5 | 6.1 |
| DeltaNet recurrence (verify and commit replay), conv, gating | 4.2 | 7.5 verify + 0.9 commit |
| Narrow BF16 (β/α, the drafter's fc and conv projections) | 3.5 | 0.8 + drafter |
| Norms, activations, FP16 conversion, other drafter kernels, top-k | 4.6 | ~3 |
| GPU idle inside the step | 3.4 | ~1 |
| **Step** | **116.8** | **105** (110 traced) |

- **Target GEMMs are now faster than production's** (17.6 GB in ~82 ms, ~215 GB/s, against 204). Three things matter here:
  - **The access pattern, not the arithmetic.** A pure read with `stream_gemm`'s row-major addressing streams at 215 GB/s, a contiguous read at 232–235. Storing the weights in kernel order (each warp load 512 contiguous bytes, scales beside their values: the spec's tiled layout) gave +5–6% end to end.
  - **Fusing launches.** Matrices that share an input go out in one launch: q|k|v, in_qkv|in_z, gate|up.
  - **What measured nothing.** Split-K, one or two tiles per warp, and prefetching 2 or 3 chunks ahead made no difference beyond the ±5% run-to-run noise.
- **Attention is the largest remaining gap.** It runs on tensor cores (BF16 `mma.sync`, `cp.async` double buffering, `ldmatrix.trans` for V) over fixed 4096-key ranges and streams the BF16 KV at ~180 GB/s; production reads it at ~260.
  - Smaller ranges lose more to partial outputs than they gain in parallelism (at 24K, 16 rows: 1024 keys 0.63 ms per layer, 4096 keys 0.57).
  - Deeper `cp.async` pipelines and a head-major KV layout were no faster.
  - A benchmark with an all-zero KV cache read ~20% faster than real data, so the numbers above use random data.
- **The DeltaNet state traffic is half production's,** as spec §9 planned. The verify reads the state and does not write the 16 intermediate states; the commit replays the accepted rows.
- **Verify width is nearly free.** At 16 rows the step costs little more than at 12 (section 4), so the engine keeps 16 draft rows where SGLang gains from 12.

## 6. The context lookup

The matcher (`lookup.cpp`) takes the last 3 tokens of history plus anchor, finds their most recent earlier occurrence, and proposes what followed it, up to B − 1 tokens. It costs microseconds. In *shadow* mode it runs on every step of the main-set replay. Its proposal is scored afterwards against what was actually generated (the leading tokens that match), and set beside what the drafter's verified chain accepted on the same step. Steps are bucketed by how far back the match reaches before the 3 tokens: a long match is a verbatim copy in progress.

| Match length | Steps with a proposal | Lookup would accept | Drafter accepted |
| --- | --- | --- | --- |
| 3 | 417 | 0.45 | 4.46 |
| 4–7 | 500 | 1.32 | 5.51 |
| 8–15 | 388 | 2.55 | 6.17 |
| 16–31 | 226 | 4.59 | 7.23 |
| 32+ | 158 | 6.87 | 9.89 |

Main set, block 16, 4,500 steps, 1,689 of them with a proposal.

- **The drafter wins in every bucket,** even on 32-token-plus verbatim copies (9.89 accepted against 6.87). DFlash2 attends to the same context and copies well already.
- **Swapping chains loses.** Verifying the lookup's chain instead of the drafter's on a long match (*auto* mode) would cost acceptance, even counting the drafter pass it saves: 7.9 tokens in ~135 ms against 10.9 in ~146. It is implemented and off.
- **A second branch gains little.** The best of the two per step is 4.14 accepted drafts against the drafter's 3.98: **+4%**, and that is an oracle bound. A second branch in the same verify (a tree) could not gain more. Spec §10's simulated ×1.2 (6.2 accepted per step) assumed the two sources succeed independently. On this workload they succeed on the same spans.
- **For M2:** the lookup branch is worth at most ~4% here. The selector's alternatives at uncertain positions, the other half of the spec's tree, remain unmeasured.

## 7. Next

In order of measured payoff per step at the workload's ~24K context:

1. **Attention: ~9 ms, against 6.1 in production.** The kernel streams the BF16 KV at ~180 GB/s. Two routes:
   - bulk (TMA) loads instead of 16-byte `cp.async`;
   - spec §16.10's FP8 KV with calibrated per-layer scales: half the bytes, but it changes numerics, so it needs the needle check.
2. **One graph per step, and the small kernels (~8 ms).** About 1,400 launches, 3.4 ms of GPU idle per step, and small kernels on the critical path:
   - the DeltaNet recurrence (verify and replay), the narrow β/α projections, norms, conversions.

   Spec §16.7's programmatic dependent launch and a captured graph are the next step.
3. **The drafter's pass over the 0.72 GB target head (~3.3 ms):** spec §10's 32k-token drafter head (M3), with its acceptance cost measured.
4. **The NVFP4 projections (spec §16.2):** −3.2 GB per pass, ~−15 ms. It needs the quality gate on the all-NVFP4 checkpoint first.
5. **Prefill** (lever 3), which sets a warm request's time to first token (section 4).
6. **Tree drafts (M2):** the selector's alternatives at uncertain positions. Section 6 shows the lookup branch is worth at most ~4% here.
7. **Batching (lever 5).** ling-serve runs one sequence; production's two-stream condition (34 tokens/s per stream, M0) is not yet comparable.

## How to run

```bash
M=~/.cache/huggingface/hub/models--RadixArk--Qwen3.8-27B-NVFP4/snapshots/<rev>
D=~/.cache/huggingface/hub/models--maurienne-ai--Qwen3.8-27B-DFlash2-NVFP4-RTNcal/snapshots/<rev>
./build/ling-stream-tests [--bench]      # kernels: accuracy, row invariance, bandwidth
./build/ling-spec-tests                  # acceptance rule (chi-square), lookup
./build/ling-run --model $M --draft $D --chat "..." --spec                 # speculative decoding
./build/ling-run --model $M --draft $D --prompts-file F --spec-check      # greedy exactness and state check
./build/ling-serve --model $M --draft $D --draft-block 16 --port 8300 --max-context 65536
```

The replay is M0's harness, unchanged (`bench/replay/replay.py` against the server's port). `bench/replay/spec_report.py` reads `/spec_stats` before and after a run, and `bench/profile/step_breakdown.py` attributes a traced step's GPU time to kernel families.
