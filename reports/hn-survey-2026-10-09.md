# HN survey: what Hacker News offers ling-engine

October 9, 2026 · reading only: no kernel was built, no GPU was used, nothing was posted to Hacker News. This is the HN part of the survey. The other parts are [research-2026-10-09.md](research-2026-10-09.md) (arXiv), [github-survey-2026-10-09.md](github-survey-2026-10-09.md) (code) and [engine-issues-2026-10-09.md](engine-issues-2026-10-09.md) (SGLang and vLLM issue trackers). This report does not repeat the arXiv part: where an item overlaps a paper there, it says so and adds only what HN contributes. It was written in parallel with the GitHub and issue surveys, so overlaps with those are not marked. HN's contributions are of three kinds:
- engineering write-ups from people running this model, or this machine;
- first-hand GB10 numbers, with their breakages;
- what local-model users say they need.

Engine numbers used for comparison come from [M1.md](M1.md) §5 and [M2-prefill.md](M2-prefill.md) §5–7:
- **Decode step:** 115 ms against production's 105.5. Within it, weight GEMMs take 81.7 ms at 215 GB/s, verify attention 11.5 ms at 31K (KV read at ~180 GB/s), the drafter 10.4 ms, small kernels 3.9 ms, commit 3.4 ms and GPU idle 3.4 ms.
- **Acceptance:** 5.2 tokens per step, which is ~45 tokens/s.
- **Prefill:** 2,640 / 2,580 / 2,110 tokens/s at 1K / 8K / 35K.

**Our estimates** are marked as estimates. Numbers quoted from HN are the poster's own, measured on the poster's hardware.

## Summary

1. **The closest public competitors on this exact model and machine are at or below the engine.** Every 2026 report of Qwen3.8-27B (or 3.6-27B) on one GB10 falls in two bands:
   - vLLM, SGLang or llama.cpp with MTP or DFlash2: 15–30 tokens/s in mixed use ([49341297](https://news.ycombinator.com/item?id=49341297), [49378710](https://news.ycombinator.com/item?id=49378710), [49554520 comment](https://news.ycombinator.com/item?id=49559658));
   - code-heavy runs of tuned recipes: ~40–70 ([49899506](https://news.ycombinator.com/item?id=49899506), [49973521](https://news.ycombinator.com/item?id=49973521), [48041555](https://news.ycombinator.com/item?id=48041555)).

   The engine's ~45 tokens/s on replayed agent sessions at 25K context is in the top band. Nobody else reports on long agent contexts, so no number is like for like (table in section 5). Two engines built for exactly this pairing (Qwen3.8-27B NVFP4 + DFlash2 on GB10) were published this year (VeloGB10 in October; Atlas's README covers Qwen3.8, so August or later): VeloGB10 and Atlas. They are the ones to watch and to read.
2. **The decode gap to production is in the places HN practitioners point at.** Verify attention: prefetch deep enough to hide ~1,000 cycles of latency, merge partials inside the kernel, use 16-byte streaming loads (item 1). Launch gaps: build each step's metadata inside the graph, and keep accept and commit on the device (item 3). The drafter's head: a frequency-ranked draft vocabulary (item 4). All three are exact. Our estimate is −6 to −10 ms per step together, which would bring the step to ~105–109 ms: parity with production, not a lead.
3. **FP8 KV is the biggest single decode lever, and HN has the clearest guidance on doing it safely** (item 5). Quantize a page only after its tokens are accepted, and keep the open tail and verify rows in BF16. Keep two boundary attention layers in BF16. Treat K more conservatively than V. Gate on tool-call replays and full-model output, never on a kernel oracle. One GB10 engine's NVFP4 KV passed its kernel test and still corrupted full-model text.
4. **For users, time to first token on a warm agent turn matters more than decode.** Real agent traffic on GB10 ran 58:1 prompt to completion tokens. The bugs that lose a hybrid model's prefix cache each cost a full re-prefill: unique IDs in the system prompt, interrupted replies not committed, unmatchable checkpoints evicting good ones, template changes to earlier turns. Item 2 turns them into tests.
5. **HN documents three ways a GB10 engine fails silently**:
   - token corruption with MTP plus CUDA graphs;
   - greedy speculative output differing from plain decode because a different verify shape changed the reduction order;
   - an image that produced token soup while "the health check was green".

   The engine's row invariance already avoids the second. The graph-per-step work needs a test for the first (item 3). Item 6 is a vendor-verifier-style quality gate.
6. **Settled by HN, not worth building here** (section 4):
   - a megakernel at a 115 ms step;
   - compressing KV by arithmetic coding;
   - Orthrus-style dual-view drafting;
   - persistent n-gram caches;
   - Q4 KV.

## 1. Method

**Search.** HN Algolia API with curl, no login, about one call per second. The window was stories created after 2025-10-09 (`created_at_i>1759968000`), with exact matching (`typoTolerance=false`).
- **Topic queries:** 126 terms, each run twice, as `search` with `points>=50` and with `num_comments>=20`, then unioned. The terms covered speculative decoding, drafters and MTP; FP4/FP8 and Blackwell kernels; linear attention, DeltaNet and hybrid models; megakernels, CUDA graphs and prefix caching; the engines (llama.cpp, vLLM, SGLang, MLX, TensorRT-LLM, Ollama, LM Studio); Qwen 27B; unified-memory machines.
- **GB10 queries, any score:** 11 terms run with `search_by_date`: DGX Spark, GB10, Grace Blackwell, Ascent GX10, Dell Pro Max GB10, EdgeXpert, ThinkStation PGX, Spark DGX, DGX Station, Nvidia Spark, Spark GB10.
- **Discarded pass:** a first pass with Algolia's default typo tolerance returned 2,260 stories ("GEMM" matched "Gemma", "DFlash" matched "Flash") and was replaced by the exact pass.

**Screened:** 971 stories (810 from topic queries, 161 from GB10 queries), by title and domain.

**Read:** 168 threads in full through `/api/v1/items/<id>` (about 12,000 comments), and 132 linked articles fetched with curl and converted to text:
- every GB10 or DGX Spark story that is about the machine, whatever its score, except GB300 "DGX Station" pieces, "RTX Spark" consumer-chip news (grepped for GB10 comparisons only) and unrelated "Spark" hits;
- 100+ topic threads.

Ten parallel readers each took one theme and returned notes; every quote and number used here was checked against the saved text.

## 3. The top 10 in depth

### 1. Verify attention that hides the latency

**What HN offers.** AMD's decode-attention guide ([article](https://rocm.blogs.amd.com/software-tools-optimization/gluon-attention-decode-mi450/README.html)) is the most complete public walk-through of a bandwidth-bound decode attention kernel. It reaches "17.10 TB/s, 85% of the peak" on MI450 at batch 64 with FP8 KV, so the magnitudes do not transfer. Four of its mechanics do:
- **Split-k sized to the hardware.** The grid grows from B·H_kv to B·H_kv·S because B·H_kv alone cannot fill the machine.
- **A latency model for prefetch depth.** One iteration has "320" cycles of compute against an assumed "1000-cycle" load latency. Double buffering leaves "about 680 cycles of exposed wait", triple buffering "about 360".
- **Wide loads.** The innermost dimension of each bulk load is ≥128 B, and 256 B is recommended.
- **The split merge fused into the kernel.**

The ds4-nvfp4-spark measurements ([48635329](https://news.ycombinator.com/item?id=48635329)) add the GB10 fact that matters:
- reads: 247 GB/s for an F32 pure read against 200 GB/s for F16/BF16, with the note "sub-word loads are slower than F32 on this controller";
- "Every real kernel tops out near 207" (read plus write);
- GEMV at M = 1: packed NVFP4 without scales 186 GB/s, Q8_0 228.

**How it maps.** The rows-path attention (M1 §5) reads BF16 KV over fixed 4,096-key ranges with `cp.async` double buffering, at ~180 GB/s against production's ~260. M1 already found that smaller ranges lose more to partial outputs (0.63 ms per layer at 1,024 keys against 0.57 at 4,096, at 24K).

It is not the SM count alone. M0 measured that 4 SMs already reach 98% of the bus on a pure read stream, and M1 found that 1,024-key ranges (about 4× the work units) were slightly slower. So the kernel is most likely limited per CTA rather than by the grid (our inference; the profile in the microbenchmark decides it):
- **Per-tile compute.** Each tile's QKᵀ, softmax and PV for 96 query rows (16 rows × 6 query heads per KV head) must hide a load latency that M0 puts at ~400 ns. That is ~1,000 cycles at 2.5 GHz, the same latency AMD's model assumes, and their model says double buffering leaves most of it exposed.
- **The cost of partial outputs.** This is what M1 measured when it shortened the ranges. Fusing the merge into the kernel (last CTA per head reduces, in a fixed order) makes finer splits cheap, and then the grid can be balanced across the 48 SMs.

The arXiv report's item 4 (PAT's structure, a ≥12-way split, partials merged through L2) proposes the same direction. HN adds the latency arithmetic, the in-kernel merge and the GB10 load-width fact.

On the target: HN posts measure pure-read ceilings of 231–247 GB/s on GB10. M0 measured 262 GB/s with streaming loads (`__ldcs`, 4 × 16 B per thread). Production's ~260 GB/s for its KV read therefore sits at M0's ceiling, which says its attention streams like M0's benchmark. The thing to check is that every KV load is a 16-byte copy with an evict-first hint, since GB10 penalizes sub-word loads.

**Exactness.** The engine's row invariance requires that a row's result never depends on how many rows share the call (M1 §3). Any new split must be a function of the key position alone: fixed range boundaries, a fixed merge order. It must not depend on M or on the context length rounded differently between decode and verify.

**Microbenchmark.** In `ling-stream-tests`, using random (not zero) KV:
1. Run the attention kernel at 24K, 31K and 64K with 16 rows.
2. Sweep the pipeline depth (2, 3 and 4 `cp.async` stages), the merge (a separate pass against a fused last-CTA merge), the work-unit count with the fused merge (8, 12, 16 and 24 ranges per head) and the load width (8- and 16-byte copies, with and without the streaming cache hint).
3. Record bytes / time, the per-SM busy fraction (Nsight Compute `sm__cycles_active`) and the stall reasons (long scoreboard against MIO throttle), which say whether loads or softmax are the limit.

**Gate:** ≥230 GB/s at 31K with output `memcmp`-identical between M = 1 and M = 16. About 3 GPU-hours.

### 2. Prefix and checkpoint robustness for real agent turns

**What HN offers.** Several owners debugged hybrid-model cache misses on their own machines.
- **qMLX** ([48876619](https://news.ycombinator.com/item?id=48876619)) fixed three bugs on a Qwen 3.5 hybrid:
  - the agent framework was "stamping a unique message ID into the system prompt on every turn", so the prompt was never byte-stable;
  - an interrupted generation was in the KV but not in the history, so the next turn diverged;
  - a background writer stored unkeyed checkpoints every 256 tokens, and oldest-first eviction then removed the one good checkpoint.

  A repeated 32K prompt "costs 88 seconds of prefill every single time. With it on, 0.64 seconds."
- **Ask HN** ([48542100](https://news.ycombinator.com/item?id=48542100)):
  - [lambda](https://news.ycombinator.com/item?id=48547922) explains that hybrid engines keep few state snapshots, and that "the tokens generated autoregressively don't always parse the same when doing prefill";
  - [LoganDark](https://news.ycombinator.com/item?id=48546415) names a harness that mutates its system prompt every turn.
- **Templates:** [ttoinou](https://news.ycombinator.com/item?id=47123453) reports Qwen's tool template changing past chats, which forces reprocessing from scratch.
- **Traffic on GB10** ([49508834](https://news.ycombinator.com/item?id=49508834), four GB10s):
  - "prompt tokens outweigh completion tokens roughly 58:1";
  - a warm re-prefill of a ~19K-token turn takes about two seconds.
- **Hit rates:** owners and hosts report 90–97% prefix hit rates on agent loops ([49739769](https://news.ycombinator.com/item?id=49739769), [49744344](https://news.ycombinator.com/item?id=49744344)).
- **MiMo** ([48814170](https://news.ycombinator.com/item?id=48814170), [article](https://mimo.xiaomi.com/blog/mimo-v2-5-inference)) found that a drafter not run during prefill left "the first 128 decode output tokens" with "very low prediction acceptance rates". The engine already tracks the drafter's context KV window (`dkv_lo_`, M2 §4); keep a test for it.

**How it maps.** ling-serve's checkpoints (M2 §4) are the end of the first two messages, multiples of 2,048, and the end of the previous prompt, in 8 slots. The new tests:
1. **Re-tokenization.** Resume after a turn whose reply is re-sent as text, and check that the prefix match is on the token ids the engine generated, or that re-tokenizing them is the identity on the replay set.
2. **Interrupted replies.** A client disconnect mid-reply must leave the history and the state consistent: either the partial reply is committed, or the state rewinds to the last checkpoint.
3. **Eviction.** The checkpoint at the end of the shared system message must survive eight sessions in rotation. Keep it pinned, or keep it as an interior node.
4. **Template and effort changes.** Measure on the replay how often a turn misses, and by how many tokens. Mightling's harness controls the prefix (SPEC §15 already lists this risk; M4 measures the hit rate).

`api.cpp` and `chat_template.cpp` own the rendering; `engine.cpp` owns the checkpoints.

**Exactness.** Exact. `--prefix-check` already proves resumption bit for bit.

**Microbenchmark.** None on the GPU. Add a replay mode that reports, per request, the resume position against the longest common token prefix with any earlier request. Report the miss rate on the 168 recorded sessions, and how many tokens each miss re-prefilled.

### 3. One graph per step, done the way SGLang did it

**What HN offers.** The LMSYS day-0 DeepSeek-V4 write-up ([47905768](https://news.ycombinator.com/item?id=47905768)) describes three things that removed the per-step overhead that "would otherwise dominate speculative decoding":
- **In-graph metadata.** Each graph replay takes only raw batch state "copied into fixed buffers", and captured kernels rebuild the rest.
- **Overlap scheduling** of CPU result processing with the GPU.
- **Hierarchical multi-stream fan-out.** At small batch, each attention-preparation kernel "underfills the GPU", so they are spread across CUDA streams inside the graph.

It also sized speculative ring buffers so that rejected writes cannot overwrite live state (8 → 16 slots).

Kog ([48321076](https://news.ycombinator.com/item?id=48321076)) keeps sampling on the GPU, with the CPU only streaming output. Its persistent monokernel is the wrong trade at a 115 ms step: [joefourier](https://news.ycombinator.com/item?id=48326137) points out that launch overhead shrinks as a share once a step verifies many tokens.

A GB10 forum thread lists "intermittent token corruption with MTP + CUDA Graphs" ([48377425](https://news.ycombinator.com/item?id=48377425)). The "What happens when you run a CUDA kernel?" write-up ([48718863](https://news.ycombinator.com/item?id=48718863)) is a reminder that lazy module loading puts first-launch costs into the first request.

**How it maps.** SPEC §8 already reads lengths from device memory, so one graph serves every context. The remaining 7.3 ms of small kernels plus GPU idle (M1 §5) is the target. Concretely:
- the DeltaNet commit plan, the drafter's context window start and the attention range count are computed on the device from the accepted count;
- `accept.cpp`'s decision moves into a device kernel;
- the drafter's small kernels and the β/α projections overlap on a second stream captured in the same graph;
- `CUDA_MODULE_LOADING=EAGER`, or a warm-up before serving.

The arXiv report's item 9 (a persistent step) comes after this. HN agrees that the graph comes first.

**Exactness.** Exact by construction. Add a graph-replay stress test:
- 10,000 steps with random accept counts (0–15) and context growth across the 4,096-key range boundaries;
- compare tokens and DeltaNet state with an eager run.

That is the case the forum report describes.

**Microbenchmark.** Nsight Systems on 60 steps at 31K (`bench/profile/step_breakdown.py`), before and after:
- **report:** GPU idle inside the step, and the small-kernel total;
- **gate:** idle ≤ 1 ms, as production has.

### 4. Frequency-ranked draft vocabulary

**What HN offers.** VeloGB10 ([49973521](https://news.ycombinator.com/item?id=49973521)) serves this target and drafter on GB10. It says optimization there "means fewer bytes (NVFP4, fused projections, frequency-ranked draft vocabularies), not fewer launches". Its measured numbers for this model on one node:
- above 40 tokens/s on average (mixed ~25–26, code ~70);
- a measured sustained bandwidth of ~238 GB/s.

Gemma 4's small drafters use "an efficient clustering technique in the embedder" because "the final logit calculation becomes a big bottleneck" ([48024540](https://news.ycombinator.com/item?id=48024540)).

**How it maps.** M1 §2: the drafter's 15 positions go through "the *target's* NVFP4 LM head". The pass over that 0.72 GB head sits inside the drafter's 7.4 ms of GEMMs (M1 §5); at 215 GB/s it costs ~3.3 ms. SPEC §9–10 already prescribes a 32k-token FP8 head (0.16 GB, ~0.75 ms), measured in M3 with a 64k fallback. HN adds two things: a GB10 engine for the same pair ships this, and the selector's top-16 candidates only need to exist inside the subset. `drafter.cpp` and `draft_kernels.cu`.

**Exactness.** Exact. Verify is unchanged. Under sampling, the selector's 16-way q is computed over the subset, which is the q passed to rejection sampling (`accept.cpp`), so no bias.

**Microbenchmark.**
1. Build the subset from the recorded sessions' token frequencies (32k and 64k).
2. Score acceptance in shadow mode on M0's main set, the way `lookup.cpp`'s shadow mode scores proposals: the subset's top-16 and path against the full head's.
3. Time the head pass.

**Gate:** acceptance loss ≤ 0.2 tokens per step (SPEC §10's threshold) and ≥ 2 ms saved. About 1 GPU-hour.

### 5. FP8 KV, built the safe way

**What HN offers.**
- **KVarN** ([48399974](https://news.ycombinator.com/item?id=48399974)), on Qwen3.6-27B with a DFlash drafter, quantizes only the full-attention layers, and "a block is committed to the quantized cache only once all of its tokens are accepted, so rejected draft tokens never corrupt history". It applies a Hadamard rotation before quantizing and gives K more bits than V.
- **Atlas** (48041555) defaults to FP8 E4M3 KV with `--kv-high-precision-layers auto`, which keeps the two boundary attention layers in BF16.
- **Failures:**
  - sparkinfer's NVFP4 KV record "passes its isolated numerical oracle, but produced corrupted full-model text" ([49650102](https://news.ycombinator.com/item?id=49650102));
  - the Level1Techs study found "int8 kv-cache eventually managed to recover, int4 did not!" on a tool call ([49402232](https://news.ycombinator.com/item?id=49402232));
  - users say quantizing K "leads to broken json on tool calls" ([lloyd-christmas](https://news.ycombinator.com/item?id=48550393)).
- **Kernel matters:** llama.cpp's q4_0 KV on GB10 lost 37% of decode at 110K ([47583555](https://news.ycombinator.com/item?id=47583555), [article](https://github.com/Memoriant/dgx-spark-kv-cache-benchmark)), because its dequant is not free. A quantized KV pays only with conversion inside the attention inner loop.

**How it maps.** SPEC §11 and §16.10 plan paged FP8 KV with calibrated per-layer scales. The HN additions to the plan:
- the page that holds the open tail and the 16 verify rows stays BF16, and is quantized when it is full and accepted; this fits commit-by-replay;
- the first and last attention layers start in BF16;
- K and V get separate scales;
- the acceptance test is item 6's tool-call replay plus long-output stress, not perplexity.

At 31K, the BF16 KV the verify reads is ~2 GB per step (16 layers × 4 KB × 31K). FP8 halves it.

**Exactness.** Not exact against BF16 KV. The engine's own invariant (greedy speculative equals greedy plain decode) still holds if both paths use the same cache.

**Microbenchmark.** After item 1:
- run attention with FP8 KV at 31K and 64K;
- **gate:** ≥ 1.7× fewer milliseconds than BF16;
- then item 6's gate on the replay set.

About 2 GPU-hours plus the quality run.

### 6. Vendor-verifier-style quality gate

**What HN offers.** Each source contributes one part of the gate:
- **Kimi vendor verifier** ([47838703](https://news.ycombinator.com/item?id=47838703)) runs sampling-parameter pre-checks before anything else, a long-output stress run that "Catches KV cache bugs and quantization degradation that short benchmarks hide", tool-call trigger F1 and JSON-schema accuracy.
- **Unsloth's "Divergence-300 @32"** (49365443): greedy decoding from 300 agentic and long-document prompts, compared with BF16 over 32 tokens.
- **ByteShape** (49749393) measures KLD "on response tokens only", over the top-k only, per request, and found KLD rankings do not match benchmark rankings. [kmike84](https://news.ycombinator.com/item?id=49617000) adds that KLD on agentic traces is much higher than on chat or wiki text.
- **Level1Techs** (49402232) found, by teacher-forced logit captures on ~100K-token agent sessions:
  - attention backends diverging in clusters;
  - a loader that "added one in the BF16 loader and stored the already-rounded effective scale" for Qwen's `(1 + w)` RMSNorm, zeroing 1,539 offsets.
- **Same model on GB10** ([49378710](https://news.ycombinator.com/item?id=49378710)): greedy speculative output on llama.cpp diverged from plain decode on 2 of 8 tasks, because "a different verification batch shape changed floating-point reduction order and flipped the argmax".

**How it maps.** ling-engine already has the strongest form of the last check (`--spec-check`, bit for bit), and `bench/validate_v0.py` measures top-1 agreement with production. Add:
1. **Norm audit.** `1 + w` is formed in FP32 from the BF16 offset in every `(1 + w)` norm: layer norms, q/k norms, the final norm. The drafter's norms are plain `x · w` (M1 §2).
2. **Divergence@32** on 300 replayed agent prompts against production's SGLang (teacher-forced, as `validate_v0.py` does).
3. **Tool-call replay.** Generate the recorded sessions' tool calls and score schema validity and argument literals (paths, flags, numbers).
4. **Long-output stress** at 25K–100K filled context.

This is the gate for items 3, 5 and 9, and for any NVFP4 projection change (SPEC §16.2).

**Exactness.** Measurement only.

**Microbenchmark.** Not a kernel benchmark: about 2–3 GPU-hours per candidate build on the development GB10.

### 7. Acceptance diagnostics, then drafter alignment

**What HN offers.**
- **vLLM on AMD** ([49596054](https://news.ycombinator.com/item?id=49596054)):
  - DFlash on Qwen3.6-27B: mean accepted length 5.19 at 7 drafts, 5.96 at 11 and 6.27 at 15 on HumanEval, bonus token included;
  - cumulative acceptance by position at N = 15: 89, 75, 62, 52, 43, 36, 31, 27, 23, 20, 18, 15, 14, 12, 10%.
- **Precision mismatch** (piszczek, [49331607](https://news.ycombinator.com/item?id=49331607)): on Qwen3.8-27B, raising the MTP head's precision against a quantized target dropped acceptance from 48.3% to 33.1% ("Standalone precision lost to quant-drafter alignment").
- **Training data** ([zackangelo](https://news.ycombinator.com/item?id=49556501)): acceptance depends on how well the output distribution matches the drafter's training data.
- **Context length:** Orthrus's README claims DFlash degrades with context ([48154865](https://news.ycombinator.com/item?id=48154865)).

**How it maps.** M1 measured 5.21 per step on the main set and 5.85–5.89 greedy on 12 prompts. Workloads differ (agent turns at 25K, 71% tool-call arguments), so 6.27 is not a target. But three diagnostics are cheap with `/spec_stats` and need no new code paths:
- acceptance per position;
- acceptance against context length (1K / 8K / 25K / 35K);
- acceptance per output type (tool arguments, code, prose, reasoning).

If acceptance falls with context, or on NVFP4-specific tokens, the arXiv report's Draft-OPD and carryover items (5–6) are the fix. HN's piszczek result is the practitioner evidence that aligning the drafter to the quantized target matters more than drafter precision.

**Exactness.** Exact.

**Microbenchmark.** A replay with per-step logging (no GPU time beyond the replay itself, ~1 hour).

### 8. Host thread on a fast core, CPU quiet during a step

**What HN offers.**
- **Chips and Cheese** ([46443626](https://news.ycombinator.com/item?id=46443626)): "Latency from the CPU side goes beyond 351 ns with the GPU pulling 231 GB/s". Core numbering starts with the A725 cores in each cluster, and cluster 1 has the larger L3.

The A725/X925 split is also a measurement trap: an unpinned benchmark run can land on slow cores.

**Exactness.** Exact.

**Microbenchmark.** 60 steps at 31K with the step thread on an A725, then on an X925. Report the step time and its variance, and the GPU idle inside the step. 15 minutes.

### 9. Prefill attention: FA4 tricks and a recalibrated ceiling

**What HN offers.**
- **Atlas** (48041555) ships, in its paged attention for GB10, "conditional softmax rescaling and software polynomial sw_exp (3 FMA + ldexpf instead of going through the SFU)". It lists LeanAttention-style stream-K decode as next.
- **The Register** (46401105) measured achievable matmul on GB10 at "101 teraFLOPS at BF16 and 207 teraFLOPS at FP8". The engine's prefill attention at ~51 TFLOPS is therefore about half of what BF16 can actually reach, not 42% of a 122 peak.
- **piszczek** (49331607) reports a flash-attention XOR-swizzle PR that took prefill at 32K from 759.38 to 815.64 tok/s on a Blackwell workstation card.
- **liuliu** ([46378093](https://news.ycombinator.com/item?id=46378093)) calls swizzling "the right way to solve the K transpose issue".

**How it maps.** M2 §7 item 1: the rows kernel holds 255 registers and runs one 6-warp block per SM. A software `exp` frees the SFU, and conditional rescale skips O-rescales when the row max is unchanged. Both reduce per-tile work but not registers. The register fix is the larger query tile M2 already names. The arXiv report's item 7 has the same conditional rescale from the paper side. HN's contribution is that it runs on GB10 in a shipping engine. Bank-conflict counters in Nsight Compute will show whether the `ldmatrix.trans` V path conflicts.

**Exactness.** Conditional rescale is exact in exact arithmetic. In FP32 it changes rounding only where the rescale factor would have been exactly 1. Software `exp` differs from `__expf` in the last bits. Prefill-only, so the speculative bit-identity is untouched (prefill feeds both paths). `--prefix-check` must still pass.

**Microbenchmark.** `ling-prefill-tests --bench` attention at 8K and 35K, three variants:
- conditional rescale;
- conditional rescale plus software `exp`;
- plus a 128-query tile.

Report TFLOPS and registers. **Gate:** ≥ 70 TFLOPS. About 2 GPU-hours.

### 10. Prefill GEMM references on sm_12x

**What HN offers.**
- **[benreesman](https://news.ycombinator.com/item?id=46463699)** says block-scaled NVFP4 works on the sm_120 family ("It's just not called `tcgen05`") and points at CUTLASS example `79b_blackwell_geforce_nvfp4_nvfp4_gemm.cu`.
- **The DGX Spark Handbook** ([49899506](https://news.ycombinator.com/item?id=49899506)) describes b12x, "a kernel library for sm_120 and sm_121" with NVFP4/MXFP4 GEMM and attention, used by GB10 vLLM recipes.
- **A forum post** (47828391) cites an "SM121 CUTLASS Kernel Optimization Results: NVFP4 356 TFLOPS" thread. The same post cites a playbook issue whose title says GB10 lacks TMA. M0 found TMA works on sm_121a (SPEC §15), so treat that title as wrong.
- **The 129-TFLOPS forum post** (47149791) has two lessons:
  - the activation-quantization tax dominates when activations are quantized per call;
  - hand-built scale-factor coordinates "corrupt ~10% of output elements".

**How it maps.** M2 §2 compared CUTLASS 4.5.1's example 79a: 325 against 230 TFLOPS on the FFN gate, 262 against 287 on down. It kept its own kernel because CUTLASS needs a second copy of the weights. The 356 TFLOPS claim, if real, is a ceiling above both. Reading b12x's and 79b's mainloops for how they feed `mma.sync ... block_scale` (TMA box shapes, stage counts, how many warps issue copies) is the cheap part. M2 §2's TMA plan needs the FP8 tiled layout changed first. `prefill_gemm.cu`.

**Exactness.** Exact if the K-order of accumulation is kept; `ling-prefill-tests` already checks against a double-precision product.

**Microbenchmark.** Build b12x's GEMM (if its license allows local benchmarking) and CUTLASS 79b at the FFN shapes, 2,048 tokens:
- report TFLOPS beside `prefill_gemm.cu`'s;
- only if one exceeds 330 TFLOPS on gate/up, read its pipeline in detail.

About 2 GPU-hours.

## 4. What not to pursue, and why

| Idea | Source | Why not |
|---|---|---|
| Persistent monokernel for the whole step | [48321076](https://news.ycombinator.com/item?id=48321076) (Kog) | Kog's budget is 333 µs per token, where 4.5 µs launches matter. At 115 ms per step, launches and idle are ≤ 7.3 ms, which the graph and item 3 attack for far less. Kog's own GEMMs run at "~36% MBU" against our 79% of spec. |
| Orthrus-style dual-view drafting | [48154865](https://news.ycombinator.com/item?id=48154865) | A second view through the model per round roughly doubles the weight stream on a bandwidth-bound machine (estimate: ~190 ms per round, needing ~8.6 accepted tokens to break even). It is not adapted to DeltaNet hybrids, and would need training at 27B. |
| Drafting during verify (SSD) | [47242637](https://news.ycombinator.com/item?id=47242637) | Same verdict as the arXiv report: DFlash2 conditions on the verified tokens' hidden states, and both compete for the bus. |
| Lossless KV compression by arithmetic coding | [48400151](https://news.ycombinator.com/item?id=48400151) | Decode would need a predictor pass plus entropy decoding per step; [0-_-0](https://news.ycombinator.com/item?id=48434968) explains why it does not help decode. At most it compresses cold checkpoints on disk. |
| Faster or persistent n-gram drafting | [49859982](https://news.ycombinator.com/item?id=49859982) | That work speeds up the CPU side of lookup; ours is bounded by acceptance (+4% oracle, M1 §6). Cross-session caches inflate benchmarks (49378710: a false 208 tok/s). |
| DSpark's Markov head | [48696585](https://news.ycombinator.com/item?id=48696585) ([README](https://github.com/deepseek-ai/DeepSpec)) | The DFlash2 selector already scores adjacent candidate pairs (M1 §2); DFlash 2's own write-up reports it beats DSpark's sequential correction at a fraction of the cost (49366792). |
| Q4 KV | 47583555, 47838788 | Software dequant lost 37% at 110K on GB10. Users report tool-call damage. The gain over FP8 is half again of a ~5 ms slice, at a quality risk an exact-sampling engine should not take. |
| Relaxed acceptance | [45556474 comment](https://news.ycombinator.com/item?id=45559262) | Changes outputs; the engine's contract is exact. |
| Two-node tensor parallelism | 49933234, 49973521 | A vendor claims "up to 1.7x" on two 64 GB units. Out of scope for a single-GB10 engine. |

What the table says for ling-engine:
- **On the same model, single stream, nobody beats the engine's decode on long agent contexts.** The higher numbers are code-only, or short context (Atlas: 128 tokens in), or a different model.
- **The bus ceiling others measure is 231–247 GB/s,** below M0's 262 GB/s with streaming loads. M0's 238 GB/s run with an idle server resident shows how easily the number moves. Against M0's ceiling the GEMMs' 215 GB/s is 82%, which is why item 1 and the arXiv report's item 1 still see room.
- **Decode falls with context on every engine that reports it.** On vLLM NVFP4, 11.5 → 9.8 tok/s from 0 to 100K is mild because the DeltaNet layers carry no KV. That is consistent with attention, not the weights, being the long-context lever.
- **Breakages owners hit on GB10:**
  - host-memory starvation that locked up the machine ([48705726](https://news.ycombinator.com/item?id=48705726) · [corti](https://corti.com/serving-nemotron-super-120b-with-a-1m-token-context-on-a-2-node-dgx-spark-cluster/), 45581439);
  - a driver page-leak patch circulating among owners who reboot often ([49149281](https://news.ycombinator.com/item?id=49149281));
  - page cache counted as used memory ([45770583](https://news.ycombinator.com/item?id=45770583) · [article](https://bartusiak.ai/2025/10/31/dgx-memory/));
  - misaligned 2-byte loads crashing on sm_121a (48635329);
  - hard reboots with MTP at 16K and two requests (49341297).

  Mightling's host-safety layer covers the first. The last argues for a 10-minute power and thermal soak before batching ships.

## 6. What users want

From the user-facing threads:
- [48542100](https://news.ycombinator.com/item?id=48542100) (Ask HN: replacing a hosted frontier model with a local one for daily coding, 1,318 points);
- [48721903](https://news.ycombinator.com/item?id=48721903) · [Quesma](https://quesma.com/blog/qwen-36-is-awesome/);
- [49299605](https://news.ycombinator.com/item?id=49299605) (the Qwen 3.8 27B release);
- 49324985;
- [49402232](https://news.ycombinator.com/item?id=49402232);
- [49787313](https://news.ycombinator.com/item?id=49787313) · [MacStories](https://www.macstories.net/stories/m5-ultra-mac-studio-review-the-dream-mac-for-local-ai-agents/);
- [45771870](https://news.ycombinator.com/item?id=45771870);
- [46907001](https://news.ycombinator.com/item?id=46907001).

Counts are rough numbers of distinct comments.

1. **Prompt processing and time to first token on long agent prompts (~40).** "you will watch the paint dry before seeing the first output token" ([moezd](https://news.ycombinator.com/item?id=48545424)). GB10 owners keep the machine for prefill ([InTheArena](https://news.ycombinator.com/item?id=49014672)). Within this, ~10 comments are about hybrid-model cache misses forcing full re-prefills.
2. **Tool calls, templates and parsers (~40).** "If tool calling is busted even 5% of the time, it can totally ruin the flow" ([porkloin](https://news.ycombinator.com/item?id=48544986)). Fixed templates took one user's agent success "from 67% to 92.5%" ([hadlock](https://news.ycombinator.com/item?id=49308143)).
3. **Overthinking at Qwen3.8's xhigh default (~30),** and loops (~25). One test took 21 minutes and 22,276 reasoning tokens (Simon Willison's post). Users want per-request effort that does not cost them the cache.
4. **Decode speed that holds with context (~30).** What counts as fast enough settles near 30 tok/s usable, 40–50 comfortable, and 60+ for the feel of a hosted model. Users notice decode falling from 70 to 40 as context grows ([Kostic](https://news.ycombinator.com/item?id=48544749)), and praise engines that stay flat to 250K ([ljosifov](https://news.ycombinator.com/item?id=48763354)).
5. **Quantization damage (~20),** above all to the KV cache. "It's really quite important that you don't quantise the KV cache" ([girvo](https://news.ycombinator.com/item?id=48562883)).
6. **Concurrency (~10).** Subagents and parallel worktrees; slots must not evict each other's cache ([blagui](https://news.ycombinator.com/item?id=48732352)).
7. **Stability and setup (~20):** lock-ups, driver leaks, too many flags, thermals.

**Suggested priority order for the SPEC** (a suggestion; the SPEC is unchanged):
1. **Warm-turn time to first token:** item 2's cache-robustness tests. ling-serve should also stream tool-call argument deltas as production does: M2 §5 notes that holding a call until `</tool_call>` makes the first delta late, and 71% of output is tool arguments.
2. **Tool-call and template exactness:** item 6's gate, run on every build.
3. **Decode parity, then decode that holds with context:** items 1, 3 and 4 (exact), then item 5 (FP8 KV, gated).
4. **Reasoning effort per request without losing the shared-prefix checkpoint:** item 15. Keep one shared checkpoint per effort level, or render the effort text after the shared prefix if Mightling's template allows.
5. **Batches of 2–4 with per-slot checkpoints** (SPEC lever 5).
6. **Long-run stability:** a 10-minute soak with clock and temperature logging (SPEC §16.1(4)) and host-safety limits, before batching ships.

## 7. Saved queries for the weekly "HN" digest

Each week, set `T` to the Unix time seven days ago (`T=$(date -d '7 days ago' +%s)`) and run the queries below, about one per second. The API is read-only and needs no login.

```bash
A=https://hn.algolia.com/api/v1
q() { curl -s "$A/$1?query=$(printf %s "$2" | jq -sRr @uri)&tags=story&typoTolerance=false&hitsPerPage=100&numericFilters=$3" \
      | jq -r '.hits[] | "\(.created_at[:10]) \(.points)p \(.num_comments)c https://news.ycombinator.com/item?id=\(.objectID) \(.title) \(.url // "")"'; sleep 1; }

# 1. Every GB10 / DGX Spark story, any score
for t in "DGX Spark" "GB10" "Spark DGX" "Nvidia Spark" "Ascent GX10" "Dell Pro Max GB10" "ThinkStation PGX" "EdgeXpert"; do
  q search_by_date "$t" "created_at_i>$T"; done

# 2. Topic stories with >= 50 points or >= 20 comments (run both filters, union)
for t in "speculative decoding" "DFlash" "DSpark" "MTP" "draft model" "NVFP4" "FP4" "FP8" "Blackwell" "CUTLASS" \
         "FlashAttention" "attention kernel" "CUDA graphs" "megakernel" "DeltaNet" "linear attention" "hybrid model" \
         "prefix caching" "KV cache" "llama.cpp" "vLLM" "SGLang" "MLX" "TensorRT" "inference engine" "Qwen3.8" "Qwen 27B" \
         "local LLM" "tokens per second" "unified memory" "Strix Halo" "Mac Studio"; do
  q search "$t" "created_at_i>$T,points>=50"; q search "$t" "created_at_i>$T,num_comments>=20"; done | sort -u

# 3. Comment trees for a chosen story
curl -s "$A/items/<id>" | jq -r '.. | objects | select(.type=="comment" and .text) | "[\(.id)] \(.author): \(.text)"'
```

Digest rules that came out of this survey:
- Read the linked article, not just the title. Several GB10 headlines were retracted in the article itself (47583555 v1; 45713835).
- Record the engine version and the date on every number.
- Flag numbers measured on code only, on short prompts, or with a persistent n-gram cache.
- Exact-match search (`typoTolerance=false`) is required: with typo tolerance, "GEMM" matches "Gemma".
