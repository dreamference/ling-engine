# M3: the decode step

October 9, 2026 · measured on the development GB10 (`second-puffin`), production's SGLang stopped for clean memory and timing (M0's reference container, restarted afterwards). Recorded sessions are replayed locally and never leave the machine; only aggregates are reported.

M3's plan: make the speculative step faster without moving any number the target computes. Three pieces, in order: one CUDA graph per step, programmatic dependent launch (PDL), and a faster attention kernel for the verify. Every change keeps greedy speculative output identical to plain decoding and rejection sampling exact, and every change except the attention prefetch is a switch that is off by default.

## Summary

1. **The step is ~4% shorter**, with every output bit unchanged:

   | Greedy, block 16, three runs each | 26.8K-token prompt | 34.8K-token prompt |
   | --- | --- | --- |
   | M2's configuration | 115.8 ms | 118.1 ms |
   | + L2 prefetch in the rows-path attention (default on) | 114.8 | 116.6 |
   | + step graphs (`--graphs`) | 111.8 | 114.1 |
   | + PDL (`--pdl`) | **111.1** | **113.4** |

   On M0's replayed agent sessions (main set, 144 requests, production sampling): **115.5 → 110.5 ms** per step, server-measured; at M2's acceptance that is 41.7 → 43.5 tokens/s of decode.
2. **It is still above production's 105.5 ms.** The step is now ~111 ms at the workload's context. What is left and what comes next is section 7; the weight stream is the largest single lever (~6 ms).
3. **Exactness holds** with every switch on and off: `--spec-check` (tokens and recurrent state against plain decoding), `--prefix-check`, and a new `--graph-check` that runs each prompt with and without graphs, greedy and seeded sampling, and requires the tokens, the state and the per-step acceptance to be identical, including across a 4,096-key range boundary. The graph check found one real bug on the way (section 2). compute-sanitizer (memcheck, racecheck, synccheck, initcheck) is clean with PDL off and on, after a pre-existing top-K ordering warning was fixed (section 6).
4. **The verify attention was load-bound, and two load paths were measured**: tiles through the bulk-copy engine (slower, kept off) and an L2 prefetch of the next tiles (−12% per layer, kept on). It still reads its KV at ~205 GB/s, against ~225 for a plain read of the same addresses (section 4).

## 2. Step graphs (`--graphs`)

A step has two data-dependent decisions, the walk of the selector's lattice after the draft and the accept rule after the verify, and both already ended in a synchronization. So each GPU part between them is a fixed launch sequence: the draft (~200 launches), the verify with its top-K (~1,300), and the commit (~100). Each is captured once into a CUDA graph and replayed every step. The host keeps both decisions exactly as before, so sampling code and numerics do not move; the two round trips cost a few tens of microseconds per step. What changes from step to step:

- **The position.** The kernels that take it (`attn_prepare`, `attention_rows`, the drafter's RoPE, attention and KV store) take a `kernels::DevPos` and, inside a graph, read it from device memory, written before each step.
- **Tokens.** Every copy inside a step goes through page-locked host buffers at fixed addresses, so the graphs' memcpy nodes read and write them in place. The selector reads its anchor from device memory.
- **The accepted count**, which only the commit depends on: one commit graph per count (at most 32), captured on first use.
- **The attention's grid.** Its key ranges depend on the context. The verify graph launches the ranges of the whole `max_context`; a range past a block's last key writes only an empty partial (max = −∞), which the combine already skips, so the result is bit for bit the eager launch's (checked in `ling-stream-tests`).
- **Sampling parameters.** Verify graphs are keyed by top-K; everything else is on the host.

A failed capture turns graphs off and runs the step eagerly; graphs are refused with `LING_PROFILE` (it synchronizes per phase) or `LING_KSPLIT` (it allocates). A single graph per step with the accept on the device (backlog B08) is the follow-on; it would move the sampling arithmetic onto the GPU, so it needs its own exactness check.

**The bug the graph check found.** The rows path's linear layers pick the quantized prefill path whenever the engine's `quantized_` flag is set, and `forward()` leaves it set after a prefill. So the first draft after every prompt ran the drafter's projections through the prefill path (since M2). Eagerly that was one step per prompt. A draft graph captured on exactly that step kept the prefill path for every later step. Tokens and state stayed exact (the verify corrects every draft); only acceptance fell (28 steps instead of 27 on a 200-token run), which `--graph-check` now compares. The step's launch sequences now select the rows path themselves.

## 3. Programmatic dependent launch (`--pdl`)

All of the rows path's kernels (the streaming GEMMs, norms, gates, adds, the DeltaNet kernels, attention, top-K, embed and the drafter's kernels) launch through `launch.cuh`. With PDL on, each may start while the one before it finishes. The rule that keeps it exact: every such kernel begins with `griddepcontrol.wait` before any read of a predecessor's output and before any write, and no block returns before it. The two exceptions issue only reads of immutable weights first: `stream_gemm` puts its first weight chunks in flight, `bf16_rows` prefetches its first bytes into L2.

The attention kernels are left out unless `LING_PDL_ATTN=1`: a PDL race in flash-attention kernels on DGX Spark was reported and fixed in llama.cpp (#23825) by taking those kernels out. Measured here with them in: no gain (111.6 against 111.3 ms at 26.8K, 113.2 against 113.4 at 34.8K), so they stay out.

PDL's measured gain is −0.7 ms, at the low end of the estimate.

## 4. The verify attention

M1 put attention at 11.5 ms of the step at 31K, reading its BF16 KV at ~180 GB/s. Measured first (`ling-stream-tests`, 24K context, 16 rows, random KV, one layer):

| Variant | ms per layer |
| --- | --- |
| The kernel | 0.557 |
| Without its MMAs (loads only) | 0.555 |
| Without its loads (MMAs only) | 0.31 |
| A plain read of the same K and V addresses (24 to 96 blocks, 192 to 1,024 threads) | 0.44-0.45 (~225 GB/s) |
| Smaller key ranges (more blocks): 2,048 / 1,024 keys | 0.60 / 0.66 |
| Position stride padded to 528 / 544 / 640 bytes | 0.51 / 0.58 / 0.56 |
| Tiles through the bulk-copy engine (TMA, one copy per key row) | 0.62-0.65 |
| **L2 prefetch of the tiles 2 ahead** (3 runs: 0.491-0.493) | **0.492** |
| L2 prefetch 3 / 4 / 16 ahead | 0.495 / 0.497 / 0.67 |

So the kernel is load-bound: its MMAs are hidden entirely, and the plain read shows the memory system can deliver ~225 GB/s for this pattern on a few SMs. It loses its time in the shared-memory ring. Two 32-key stages (the 99 KB per block allow no third) leave one tile in flight while the other is computed.

- **Bulk copies** (`--attn-bulk`, off): the same tiles through the TMA engine, completing on one mbarrier per stage. Bit for bit the same output, and slower at every setting tried.
- **L2 prefetch** (`attention_prefetch = 2`, on): in the head-major layout a tile's K and its V are each one contiguous run, so one `cp.async.bulk.prefetch.L2` per stream, by two threads, keeps two more tiles on their way into L2 at no shared-memory or register cost. It moves data only; `ling-stream-tests` checks the output bit for bit against the kernel without it. 0.557 → 0.492 ms per layer for a verify, 0.523 → 0.455 for one-row decode.

At ~205 GB/s it is still ~10% short of the plain read and ~20% short of production's FlashInfer (6.1 ms for 16 layers at ~24K, M0). Backlog B07 gives the next design: a ≥ 12-way split with the partials merged inside the kernel, 3-4 stages. The measurements above say the stages, not the split, are what this kernel lacks (more blocks were slower), so the next step is a ring of more, smaller stages within the same 99 KB. A 16-key tile changes the online softmax's grouping, so decode and verify move together and the result is no longer bit for bit M2's, though still exact between them.

## 6. Exactness

| Check | Result |
| --- | --- |
| `--spec-check` (5 prompts incl. 11,316 tokens; 200 tokens): no switches, `--graphs`, `--pdl`, `--attn-bulk`, all three | tokens identical, state identical, every prompt |
| `--prefix-check` (7 replayed prompts to 30,950 tokens) with `--pdl --attn-bulk` | states and next token identical |
| `--graph-check`, 2,000 tokens, greedy and seeded sampling, with and without `--pdl --attn-bulk` | 20 / 20 identical: tokens, state, steps and accepted drafts |
| `--graph-check` across a 4,096-key range boundary (a 28,578-token prompt, 600 tokens past key 28,672), greedy and sampled, without and with `--pdl` | identical: tokens, state, steps and accepted drafts |
| `ling-stream-tests`, plain, `LING_PDL=1`, and 50 runs with `LING_PDL=1 LING_PDL_ATTN=1` | all pass (50 / 50), including the new bit-for-bit checks: device-position attention, bulk tiles, L2 prefetch |
| compute-sanitizer memcheck, racecheck, synccheck, initcheck on `ling-stream-tests`, PDL off and on; memcheck on `ling-run --spec --graphs --pdl` | 0 errors (racecheck after the top-K fix below) |
| Debug build (`-G`) `--spec-check --graphs --pdl` (4 short prompts, 32 tokens) | tokens and state identical (after the launch-bounds fix below) |
| `ling-spec-tests` (chi-square), `ling-api-tests` | pass |

Two pre-existing problems surfaced and are fixed:

- **racecheck** warned on every top-K launch: the lanes read the list's count and threshold, a ballot follows, then lane 0 updates them. A ballot synchronizes lanes but does not order memory. A `__syncwarp` before the ballot orders them; no value changes.
- **The Debug build** failed to launch the two 1,024-thread norm kernels (more than 64 registers per thread under `-G`); `__launch_bounds__(1024)` keeps them in the register file.

Nothing in M3 changes what the target computes: graphs and PDL launch the same kernels, the prefetch and the bulk tiles move data only, and the one behavioural fix concerns the drafter. M2's agreement with production (SPEC's standing gate) is therefore unchanged.

## 7. What's left, in order of expected payoff

The step is ~111 ms at the workload's context, ~5.5 ms above production's 105.5.

1. **The weight stream (~6 ms).** 17.6 GB at 215 GB/s, where a plain read reaches ~225-235 here and others measure 231-235 GB/s on GB10 (backlog B16). It is 70% of the step.
2. **The attention's stages (~1-1.5 ms at 27K).** Section 4: more, smaller stages, or the kernel restructured as backlog B07 describes.
3. **The small kernels (~1.5 ms).** `to_half_rows`, `add_inplace` and `silu_mul` folded into the kernels that produce their inputs and into the GEMM epilogue; all row-invariant.
4. **The commit beside the next draft (~2 ms).** The DeltaNet replay is independent of the drafter's pass; a second captured stream can run it there, joining before the verify.
5. **One graph per step with the accept on the device** (backlog B08), then the persistent step (B32).
6. The drafter's 32k-token head (B25), outside M3, takes ~3 ms of the drafter's pass at a measured acceptance cost.

## How to run

```bash
M=~/.cache/huggingface/hub/models--RadixArk--Qwen3.8-27B-NVFP4/snapshots/<rev>
D=~/.cache/huggingface/hub/models--maurienne-ai--Qwen3.8-27B-DFlash2-NVFP4-RTNcal/snapshots/<rev>
./build/ling-stream-tests [--bench]           # kernels; LING_PDL=1 with PDL, LING_NO_TIMING=1 under compute-sanitizer
./build/ling-run --model $M --draft $D --prompts-file F --spec-check [--graphs] [--pdl] [--attn-bulk]
./build/ling-run --model $M --draft $D --prompts-file F --max-tokens 2000 --graph-check --seed 7 [--pdl]
./build/ling-run --model $M --draft $D --prompts-file F --spec --graphs --pdl     # [--attn-prefetch 0] for M2's attention
./build/ling-serve --model $M --draft $D --port 8300 --max-context 65536 --graphs --pdl
```

Switches: `--graphs` / `LING_STEP_GRAPHS`, `--pdl` / `LING_PDL` (and `LING_PDL_ATTN` for the attention kernels), `--attn-bulk` / `LING_ATTN_BULK`, `--attn-prefetch N` / `LING_ATTN_PREFETCH` (default 2). Traces need Nsight Systems 2025.3.2 with `--cuda-graph-trace=node`; 2026.3.2 records no graph-node kernels (M0).
