# ling-engine: Backlog from user requests

Part of the ling-engine specification; the index is [README.md](./README.md). Section numbers are those of the single-file `SPEC.md` this was split from (Oct 8, 2026 · revised the same day against Mightling's measured workload), so a citation of the form `§n` or `S§n` in the reports and the code still names the same text.

## 19. Backlog from user requests

What users of SGLang and vLLM asked for, and what the four clients send that ling-serve does not handle ([reports/api-compat-checklist.md](../reports/api-compat-checklist.md)). Ranked for one owner on one GB10 running 1–4 agents.

1. **Context overflow the clients can recognise.**
   - Chat completions and completions: HTTP 400 before any header, code `context_length_exceeded`, with a message that matches LiteLLM's patterns ("maximum context length is …").
   - The Responses API: `response.failed` with that code, the only shape Codex compacts on.

   Today Codex retries the same prompt five times and OpenHands for two minutes; neither compacts.
2. **Images.** Answer with a placeholder instead of a 400 until the vision encoder (M4) lands (done 2026-10-10: an image part renders as `[image]` on both routes, [API §7](./DREAMFERENCE_LING_ENGINE_API.md)), and set `input_modalities: ["text"]` in the launcher's catalog meanwhile (still open). Codex treats a 400 as the end of the turn. The encoder itself is item 16.
3. **Stream fixes:**
   - hold back stop-string output to a character boundary;
   - end every started stream with a finish chunk and `[DONE]`;
   - validate before sending headers.
4. **Cancellation before work.** Check the cancel flag before dequeuing and between prefill chunks. With one worker, an abandoned 30-second prefill delays every agent.
5. **A NaN guard** ([section 18](./DREAMFERENCE_LING_ENGINE_VALIDATION.md)) with a counter in `/metrics`.
6. **Parser fixes** from [section 18](./DREAMFERENCE_LING_ENGINE_VALIDATION.md):
   - fences;
   - unoffered names;
   - prose before a call;
   - unclosed middle parameter;
   - unrenderable history arguments rendered instead of refused (done 2026-10-10, the owner's decision, [API §3](./DREAMFERENCE_LING_ENGINE_API.md): the string is written verbatim where the parameter blocks would go, because the broken arguments are what the model emitted on an earlier turn, clients replay history unchanged and Codex ends the turn on a 400; ling-serve's own parser never emits them. Production refuses, SGLang 0.5.19 and 0.5.21 answering 400 "Assistant tool call function.arguments must be valid JSON." before the template; this is the one place ling-serve knowingly renders a prompt production would not).
7. **Small request fixes:**
   - presence and repetition penalties over output tokens only;
   - `reasoning_effort: "none"` on chat completions (done 2026-10-10: thinking off, as on `/v1/responses`, [API §3](./DREAMFERENCE_LING_ENGINE_API.md));
   - `reasoning_tokens` counted (done 2026-10-10: from the token ids in the engine's loop, [API §3 and §4](./DREAMFERENCE_LING_ENGINE_API.md));
   - `reasoning` accepted as an alias of `reasoning_content` on input;
   - invalid-JSON tool-call arguments in a chat history: see item 6 (done 2026-10-10, rendered verbatim);
   - a negative `max_tokens` refused.
8. **Several resident sessions** ([section 11](./DREAMFERENCE_LING_ENGINE_SESSIONS.md)). Two interleaved agents evict each other's history today, and each then re-prefills from its last checkpoint. With several sessions resident, `prompt_cache_key` (Codex sends the thread id) is the natural session key. Upstream's equivalent complaint is lost prefix hits per turn ([vllm#53670](https://github.com/vllm-project/vllm/issues/53670), [vllm#53477](https://github.com/vllm-project/vllm/issues/53477)). **Done 2026-10-11 (M4 stage 1, [drafts/M4 §6](./drafts/M4-sessions-and-batches-2026-10-10.md)):** two resident sessions by default, `prompt_cache_key` as the session key (a hint; the token prefix decides), two alternating conversations each stay warm (`tests/server/test_sessions.py`). **The checkpoint store's full rule (the owner's decision, 2026-10-12):** the least recently used entry gives way (stage 1 dropped the latest position, so a store full of other prompts' earlier entries saved nothing new and an identical resend of a 2,080-token prompt reused nothing); an entry is used when saved and when a prefill resumes from it or extends its prefix, and a prefill never evicts an entry on its own prompt's prefix, so the shared system prompt's checkpoints stay (that refinement confirmed by the owner, 2026-10-13). Regression case: `test_used_checkpoint_store_still_saves` in `tests/server/`. **Next to that rule: tool-wait-first eviction** (the owner's decision of 2026-10-13, from the Together AI survey's §2.5, `specs/research/together-ai-survey-2026-10-13.md` in the dgxcoder repository; ThunderAgent, [arXiv 2602.13692](https://arxiv.org/html/2602.13692)). When a session slot must be given up (`Engine::free_session` takes the least recently used session that is neither pinned nor protected today), the sessions waiting on a tool call (their last response ended in a function call and no request has continued them yet) give way before those that are reasoning, the longest waiting first, and recency decides only among sessions of the same kind; the 30 s protection and the own-prefix rule stay as they are, and the checkpoint store's entries can be ranked the same way by the session that saved them. ThunderAgent measured request-level engines inflating agent latency up to 7.14× by evicting a program's state during its tool call. Exact: eviction changes only where a later prefill resumes, never what it computes. Small: one field per session (when its tool phase began, set when a response ends in a function call, cleared by the next request that continues it) and a sort key. It matters once more sessions run than stay resident (Night Shift beside an interactive session and subagents); at the one or two streams of today it rarely fires. Not yet placed in the order. **Also next to that rule: a kept state at each tool-output boundary** (the owner's decision of 2026-10-13, from the compaction survey's §3.2 and §4, `specs/research/compaction-survey-2026-10-13.md` in the dgxcoder repository). The model's recurrent layers hold one state, not per-token entries, so a prompt that drops or trims a span from the middle of the history (an agent's compaction that first drops old tool outputs, the first compaction change to be tested, as a SWE-bench night arm; or a delayed rewrite of the step two back) can only be served by replaying from the nearest kept state before the edit. Today the states kept are the end of a session's last prompt, the end of the first two messages and every 2,048 tokens up to 32,768, so such an edit replays from up to 2,048 tokens before it, or further once the history is past 32,768. Keeping a state at the end of each tool output (the `<|im_end|>` that closes a tool message, at the multiple of 32 at or before it, where a resumed prefill can start exactly) makes the replay start at the first dropped output, or at the last two steps for a tail rewrite. Exact: a resumed prefill computes the same state as one from scratch (`--prefix-check`), so the output is unchanged. What it needs: the boundary positions among the prefill's chunk ends, and room for them, since each kept state is 157 MB and the store holds 8 (more slots, or the least-recently-used rule choosing among them). Not yet placed in the order.

13. **Custom (freeform) tools for Codex. Done 2026-10-10** ([API §4](./DREAMFERENCE_LING_ENGINE_API.md)): a `type: custom` tool is offered to the model as a function with the one string parameter `input`, its grammar appended to its description as prose; the call comes back as a `custom_tool_call` item with the `custom_tool_call_input.delta/.done` events Codex parses, and `custom_tool_call` / `custom_tool_call_output` history replays as that call and its tool response (`ling-api-tests`; `test_responses_custom_tool_call_stream` and `test_responses_custom_tool_replay_matches_what_the_model_wrote` in `tests/server/`). Decided with the owner: the grammar rendered (description only was tried first: the model wrote a unified diff where apply_patch's syntax was wanted), no grammar enforcement, the whole input as one delta, Responses only (on chat completions, the vLLM-compatible route, a `type: custom` tool is dropped). **Open:** the grammar is rendered, not enforced; constrained decoding (item 11's structured output) is the remedy if the model still strays from apply_patch's syntax. Today's `ling` build sends function tools to this model in its default mode, so there the path is exercised by the tests alone until Mightling's launcher catalog offers the freeform `apply_patch`; under Code Mode `ling exec` sends its `exec` custom tool (a 177-byte grammar) today, and the operations stream runs that against `ling-serve` as the acceptance check (2026-10-10). Production SGLang drops custom tools under Code Mode: the same `ling exec` run against the M0 reference never produced a `custom_tool_call` in eleven turns, against ling-serve three in seven (the operations stream's capture, 2026-10-10; recordings under `reports/raw/code-mode-acceptance-2026-10-10/` once copied).
14. **`kernels.cu` made readable, with the SASS unchanged** (the user's request, 2026-10-09; no speed gain, so it is not in the ranked backlog). Each step is accepted only when `cuobjdump -sass` of the touched kernels is byte-identical before and after on second-puffin and `ling-kernel-tests` passes:
   - split the file by subsystem: `device_common.cuh` (`warp_sum`, `block_sum`, the FP8 converters, `silu`), then `gemv.cu` (both GEMVs and the two dequants, which share the FP4 lookup table), `attention.cu`, `gdn.cu`, `elementwise.cu`;
   - name the layouts: a small strided view built inside the kernel from the `__restrict__` parameter (never a struct member, where `restrict` is ignored) replaces the repeated `(pos * Hkv + kh) * D + d` arithmetic;
   - type the attention partial record: `struct AttnPartial { float m, l; float acc[256]; }` in place of `part[0]`, `part[1]`, `part[2 + d]` and the `(D + 2)` stride;
   - one online-softmax merge helper for the three places that rescale `(m, l, acc)`: per key, across warps, across splits;
   - a variadic launch helper that does `<<<>>>` and the launch check in one call, and one `dispatch_rows(M, f)` for the FP4 and FP8 row ladders;
   - argument structs for the wide signatures (`attn_prepare` takes seventeen parameters); a struct passed by value lands in the same constant bank;
   - a header comment per kernel: the thread mapping, each buffer's shape, the invariants the host checks.
   Not touched: the fixed-size register arrays with `#pragma unroll`, the issue-all-loads-first pattern, `__ldg` on `uint4`, `__launch_bounds__`, `fmaf` and `__expf`, the padded shared-memory stride. **Not pursued (the user's decision, 2026-10-09):** merging the FP4 and FP8 GEMV kernels into one body over a codec policy; it changes the loop structure and would need the bandwidth bench to accept, so the two kernels stay separate.
15. **Two API surfaces, no third (the owner's decision, 2026-10-10).** The goal is to match the Codex Responses API completely, and to keep a vLLM-compatible surface (`/v1/chat/completions`, `/v1/completions`, `/v1/models`, `/metrics`) for the other clients. The gaps found on 2026-10-10 against the pinned Codex source, in order: custom tools (item 13, done 2026-10-10); `usage.output_tokens_details.reasoning_tokens` always 0, which Codex displays and budgets on (item 7, done 2026-10-10); `parallel_tool_calls`, `tool_choice: "required"`, `include`, `store`, `prompt_cache_key`, `reasoning.summary` and `text.verbosity` accepted and ignored (so no `reasoning_summary_text.*` events, which Codex tolerates; item 11 for the refusals, item 8 for `prompt_cache_key`); no rate-limit headers, so Codex's usage display stays empty (harmless). **Not pursued:** a high-performance protocol of ling-engine's own. The time is not in the HTTP layer (a token every 12 to 30 ms against microseconds of framing; M3's gap is the weight stream), every client switches engines by changing nothing but the server behind the port ([INTEGRATION §12](./DREAMFERENCE_LING_ENGINE_INTEGRATION.md)), and a third surface is a third place to prove token-identity. Engine-specific routes stay additive beside the two surfaces (`/spec_stats`, the `ling:*` metrics, and later a session handle or "continue this prefix" for [SESSIONS §11](./DREAMFERENCE_LING_ENGINE_SESSIONS.md)), each justified by a measured number. **Relaxed (the owner's decision, 2026-10-12): optional speed-only extensions are allowed.** A request may carry extra arguments that only make it faster, under one rule set: (1) optional and ignorable: a request without them is served exactly as before, and every other client is unaffected; (2) they never change the output: tokens, logprobs and usage are what the same request gives without them (speculation stays exact; an extension can only change what is proposed, never what is accepted); (3) one namespaced object, `ling` (e.g. `"ling": {"lookup_corpus": …}`), on `/v1/responses` and the chat/completions routes alike, documented in [API §8](./DREAMFERENCE_LING_ENGINE_API.md); unknown keys inside it are ignored, a malformed value is a 400 naming the key; (4) a client sends it only to a server that says it accepts it (`/v1/models` `owned_by: ling-engine`, the launcher's existing gate), never to SGLang or vLLM. The first extension is item 20's repository lookup corpus.

18. **Our own TMA-fed prefill GEMM over the one copy of the weights** (scheduled for after M5; the owner's decisions of 2026-10-12: first "one copy, not two", then "our own kernel, not CUTLASS"). [M2-prefill](../reports/M2-prefill.md) measured CUTLASS 4.5.1's SM120 block-scaled NVFP4 GEMM at 2,048 tokens: 325 TFLOPS on the FFN gate against ling-engine's 262 (gate and up fused), 262 against 287 on the down projection; CUTLASS was not adopted because it reads the weights K-major with its own blocked scale-factor layout, which would need a second copy of the FFN weights (~10.7 GB on a ~57 GB budget). The gap is in how the tensor cores are fed, not in the MMA: CUTLASS loads tiles with TMA from a producer warp and syncs the consumer warps with mbarriers; M2's own warp-specialized variant issued `cp.async` copies from one producer warp and was 3–4x slower on NVFP4 (one warp cannot issue a stage's ~1,800 copies while the MMAs run). The decision: build that pipeline ourselves, with no CUTLASS in the build. TMA tensor maps over M1's tiled layout (each 16-row x 128-value block contiguous with its scales beside it, so values and scales are two strided views of the same 1,152-byte blocks; the layout the decode kernels read and which gave +5–6% end to end, kept as the one copy), one producer warp issuing TMA, consumer warps on the block-scaled MMAs, mbarriers between them, and M2's fused epilogues kept (gate and up as one GEMM writing SwiGLU's NVFP4 output). CUTLASS's example 79a stays as the benchmark to beat (325 TFLOPS on the FFN gate at 2,048 tokens; it builds and runs here unmodified), never linked. Open: the FP8 tiled layout has no 64-byte row runs for a swizzled TMA box (M2-prefill, "What did not work"), so the FP8 projections may keep today's kernel or need their layout changed; the NVFP4 FFN, where the gain is, has 64-byte rows. Gate: byte-identical output with the K order kept, prefill only, nothing on the decode path changes. Expected: −0.9 to −1.5 s on a 35K-token prefill (B33's adopted range), none on decode. This is the concrete form of `reports/backlog-2026-10-09.md` B33.
19. **The drafter's context-aware sparse head** (in the single-step savings block after M4 stage 4; the owner's decision, 2026-10-12, [§14](./DREAMFERENCE_LING_ENGINE_MILESTONES.md), "Order"). Each step the drafter scores its candidates against the full 0.72 GB target head (~3.3 ms at 215 GB/s, inside the drafter's 7.4 ms of GEMMs, [reports/M1.md](../reports/M1.md) §5 and "For M2" item 3). vLLM's context-aware sparse head ([#59740](https://github.com/vllm-project/vllm/pull/59740), [#60226](https://github.com/vllm-project/vllm/pull/60226); `reports/github-survey-2026-10-09.md` item 2) reads a fixed list of the 32k most frequent rows plus 16k rows picked per token by a rank-256 copy of the head; on Qwen3.8-27B NVFP4 on one GB10 it gave +5.9% decode at concurrency 1 with acceptance unchanged. The same source measured a *static* 32k head at −5.7% acceptance on average and −33% on multilingual prompts, so this item **replaces** [SPECULATION §10](./DREAMFERENCE_LING_ENGINE_SPECULATION.md)'s static 32k head. Expected here: smaller than vLLM's figure, because vLLM's +5.9% was measured with an MTP drafter (k = 3), which passes over the head once per drafted token, while DFlash2 drafts its whole block in one pass: the saving is the head's bytes minus the sparse head's (the 48k selected rows, ~0.14 GB, plus the rank-256 copy, ~0.13 GB in BF16), about **2–2.5 ms per step (~2–2.5%)**; measured, not assumed. Plan: (1) the rank-256 factorisation of the head and the 32k frequency list computed offline from the checkpoint and the replay sets, stored beside the drafter; (2) a selection kernel (rank-256 scores over the vocabulary, top 16k, union with the fixed list) and the drafter's head GEMM over the selected rows, both row-invariant; (3) `--draft-head full|sparse` (default full until the gate passes). Gate: the target's output is unchanged by construction (only the proposals change, the verify is untouched), so the gate is acceptance: the accepted-per-step histogram on M0's main and tuning sets at 12 drafts, single stream and two streams, within run-to-run noise of the full head, and no fall on a multilingual replay slice (the static head's −33% case); then the step time with the head in, kept only if it gains.
20. **More tokens per step: a drafter tuned on agent sessions, and the lookup branch re-measured** (the owner's decision, 2026-10-12, "plan item 4"). Two sources, two places in the order:
   - **The agent-tuned drafter** is the stretch column's ≥ 8 accepted per step ([OVERVIEW](./DREAMFERENCE_LING_ENGINE_OVERVIEW.md) targets; today ~5.2 at 12 drafts). It is trained on the product side, by Mightling's self-speeding plan (`specs/DREAMFERENCE_SELF_SPEEDING.md` in the mightling repository: Phase 0 reads acceptance per class from the production server's `/metrics` for a week; then SpecForge's DFlash2 recipe trains on the user's own sessions at night with the model server stopped; a candidate is promoted only if held-out tokens/s gains ≥ 5% with no class regressing > 3%). Because the DFlash2 drafter is the same file for SGLang and ling-engine, a promoted drafter speeds up production first, with no engine change; the engine's part is the M5 trial already in the roadmap: the promoted drafter served by ling-serve, acceptance measured under the engine's exact verify (single stream and two streams, M0's sets plus a held-out slice of recent sessions), and the shipped drafter kept as the fallback per request class (MILESTONES §15's overfitting risk).
   - **The context-lookup branch** (`--lookup`, [SPECULATION §10](./DREAMFERENCE_LING_ENGINE_SPECULATION.md)) was worth at most ~4% as a separate source ([reports/M1.md](../reports/M1.md) §6). It is re-measured inside M2's tree, as one branch of the same verify ([reports/backlog-2026-10-09.md](../reports/backlog-2026-10-09.md) B36's general proposer interface), together with MILESTONES §15's open question of a cross-session suffix store (proposals from earlier sessions' outputs). The research threshold stands: kept only at ≥ +8% on the oracle (`reports/research-2026-10-09.md`), otherwise off for good.
   - **Edits: lookup aimed at copied spans** (added the same evening at the owner's question about edits whose output repeats the input). An edit re-emits much of what the context already holds: a patch's context lines and unchanged code, a rewritten file, an old string quoted before its replacement. M1's ~4% is an average over all output, where prose, reasoning and tool calls dilute it, and DFlash2 already predicts much copied text (both sources succeed on the same spans). So the M2 re-measurement is made **per output class**, with edits separated: tool-call arguments of `apply_patch` (function and freeform), file writes and diff-shaped text, located by the template's tool-call markers in the replay. Built if it gains there: (a) lookup switched on per span, on while the output is inside an edit-shaped tool call and off elsewhere, so a gain on edits is kept even if the average stays under the +8% bar; (b) long copy branches inside an edit (the 64-token branch of MILESTONES §15), since an unchanged region can run hundreds of tokens; (c) the match anchored on the file being edited (the last read of that path in the context) before the whole context. The patch format decides how much is copyable: night 5 (apply_patch as a function tool on production, 2026-10-13) changes what the model emits for edits, and its transcripts are a measurement input here. Reference: vLLM's n-gram lookup in front of an MTP drafter gave +28% on copy probes on GB10 (`reports/github-survey-2026-10-09.md`), with a weaker drafter than DFlash2, so an upper bound.
   - **Names from the repository that the context has not shown** (the owner's question of 2026-10-12, made possible by item 15's speed-only extensions). Most names an edit writes are already in the context (the agent read the file, grepped, asked `ling-code`), so the context lookup and the drafter tuned on the user's repository cover them; the rest are names in the repository the session never read. The client (the `ling` launcher, which runs where the repository is and already has `ling-code`'s index) sends a compact lookup corpus with the request in the `ling` extension: the repository's identifiers and frequent n-grams (or a content hash naming a corpus uploaded once per session and cached by `prompt_cache_key`, so it is not resent each request), capped in size. The engine adds it as a lookup source behind the context (an identifier trie: once a name's first sub-tokens are emitted, the rest is proposed), so it is consulted only where the context has no match. Exact by construction. Measured at M2 with the other lookup sources, per output class; built only if it adds acceptance beyond the context lookup and the tuned drafter.
   - **The moonshot behind these items:** [drafts/MOONSHOT-repository-aware-decoding-2026-10-13.md](./drafts/MOONSHOT-repository-aware-decoding-2026-10-13.md) (the owner's request of 2026-10-12): five proposal sources (session, emission views of files in the context, the repository through the `ling` extension, the user's own history, the model drafter), edit mode, long verified copies of 64–128 tokens, and P0, a measurement with no build that decides whether any of it is worth doing. **Decided (the owner, 2026-10-13): GO** on P0's +7–13% whole-session gain ([reports/moonshot-p0-copy-stats-2026-10-13.md](../reports/moonshot-p0-copy-stats-2026-10-13.md)), the 20% bar dropped, and P1's whole-session gate restated as ≥ +7% with the output byte-identical (was ≥ +20%); P0's GPU half (`bench/rowsweep.py`) still runs, as design input rather than a gate. P1's GPU work (its GPU tests and first numbers) runs between the single-step savings and M4's stage 5, so stage 5 measures both together against production; its CPU parts are written now on branch `moonshot/p1` (the owner's decision of 2026-10-13, [§14](./DREAMFERENCE_LING_ENGINE_MILESTONES.md), "Order").
   Gate for both: the target's output is unchanged by construction; acceptance per class and tokens/s on held-out sessions decide.
21. **One model across both GB10s: two-node tensor parallelism** (last in the engine plan, the owner's decision of 2026-10-13, which moved it from "after M5, not scheduled" of the night of 2026-10-12: it comes after every one-node improvement is settled, M4 and the step savings, the moonshot's P1, M4's stage 5, structured output and images, M2's tree speculation, M5, the moonshot's phases and every other single-node BACKLOG item; the owner will take it up then). Decode is weight-read bound: 17.6 GB per step, ~82 ms of the ~108 ms single-stream step at ~215 GB/s ([MODEL §5.2](./DREAMFERENCE_LING_ENGINE_MODEL.md), [reports/M3.md](../reports/M3.md) §1). Splitting each layer's weights across the two machines (by output for the in-projections and gate+up, by input for the out-projections and FFN down, the LM head by vocabulary) halves the bytes and the per-head work each machine does, at the cost of two all-reduces per layer (128 per step, the DeltaNet layers included) over the DGX Spark's 200 Gb/s ConnectX-7 link. Both machines are on Wi-Fi today; this needs the direct cable. Each all-reduce carries an FP32 partial of 20 KB per row: 240 KB at one stream (block 12), 480 KB at two. That is 2–5.5 ms per step at 5–30 µs of link latency, so latency, not bandwidth, sets the cost. Estimate: **about 1.5–1.8× on decode**, to be measured; prefill gains too. A plain all-reduce is not byte-identical to one machine (`stream_gemm` adds its eight warp sums in order). It becomes exact by splitting K by warp stripe and sending the warp sums (4× the bytes), or by relaying the running sum (two latencies), each with the per-row FP16 scale's maximum exchanged as well (256 exchanges per step; ~1.4× in the worst case, a 30 µs link), or by making the one-machine order and scale two-level first (the owner's decision); otherwise it is a non-exact mode under [MILESTONES §14](./DREAMFERENCE_LING_ENGINE_MILESTONES.md)'s exactness policy. Measured first: the link's RDMA latency and bandwidth between the two Sparks, a two-node all-reduce microbenchmark at the step's sizes and as the step's chain of 128, and the half-shape GEMMs on one machine. The cost: second-puffin stops being a separate node, benchmark lane and development machine while the pair serves. The product needs both machines served as one model (the node locator, pairing, the gate, the lifecycle). The arithmetic, the exact forms and the go rule: [drafts/two-node-tp-2026-10-12.md](./drafts/two-node-tp-2026-10-12.md). It revisits [OVERVIEW](./DREAMFERENCE_LING_ENGINE_OVERVIEW.md)'s non-goal for after the first release.
22. **The drafter's NVFP4 scales re-fitted (ScaleSearch), if a measured gap justifies it** (the last item of the single-step savings block after M4 stage 4; the owner's decision of 2026-10-13, from the Together AI survey, `specs/research/together-ai-survey-2026-10-13.md` in the dgxcoder repository, §2.1 as corrected by §8.1–8.2; [MILESTONES §14](./DREAMFERENCE_LING_ENGINE_MILESTONES.md), "Order"). NVFP4 sets each 16-value block's FP8 scale from the block's maximum; ScaleSearch (MLSys 2026, [arXiv 2605.12464](https://arxiv.org/html/2605.12464)) tries the neighbouring representable scales (offsets −2 to +6) and keeps the one with the lowest block error, about 25–27% less quantization error, in the same format, read by the same kernels. **Whether there is anything to recover is unshown.** The drafter we serve, `maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal`, reports 3.60 accepted per block of 8 against 3.71 for its BF16 original, but its card calls that parity: run-to-run noise is about ±0.2, and its long-context readings go both ways (8K 3.03 against 3.12, 32K 3.32 against 3.18, 64K 3.19 against 3.44, 85K 3.21 against 3.18). GPTQ, q/k/v kept in BF16 and SmoothQuant folding were tried there without measurable gain. The drafter is W4A4 (static per-tensor activation scales), and ScaleSearch changes only the weights' block scales, so the activation half of the error is outside its reach. The "up to about 3%" first written here is an upper bound on a gap nobody has shown exists, and at our 12 drafts (the card measured block 8) the parity is untested either way. **First step:** an acceptance A/B of the BF16 drafter (3.53 GB, it fits beside the target) against the served NVFP4 one at 12 drafts on the replay set, two runs each, about 1 GPU-hour; it runs on SGLang, which loads either file (ling-engine's drafter loader reads NVFP4 projections only). Re-quantize only if BF16 wins by more than the run-to-run spread; then ScaleSearch, or a KL-to-target objective in the spirit of YAQA (survey §8.6), are the candidates, about half a day more, kept and pinned in Mightling's model matrix only if acceptance rises. If BF16 does not win, the item closes at the cost of that GPU-hour. Either way it is exact: the drafter only proposes and the target verifies every token, so the output is unchanged, and the drafter's bytes and kernels are the same, so the step costs the same. Production SGLang loads the same file, so a win carries over there too; it is also the quantization step the agent-tuned drafter of item 20 will need.
