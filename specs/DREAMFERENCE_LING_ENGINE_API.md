# ling-engine: The HTTP API of `ling-serve`

Part of the ling-engine specification; the index is [README.md](./README.md). Written on 2026-10-09 from the code (`src/serve/main.cpp`, `src/serve/api.cpp`, `src/serve/api.hpp`), which is the source of truth. What the four clients actually send, and which of it is handled, is measured in [reports/api-compat-checklist.md](../reports/api-compat-checklist.md); the gaps it found are ranked in [BACKLOG §19](./DREAMFERENCE_LING_ENGINE_BACKLOG.md).

`ling-serve` presents the OpenAI-compatible surface the production SGLang server presents for this model, so that Mightling and the other clients (Cline, Continue, OpenHands, the web chat) switch engines by changing nothing but the server behind the port ([INTEGRATION §12](./DREAMFERENCE_LING_ENGINE_INTEGRATION.md)). No authentication: the boundary is the network, as it is for production.

## 1. Model of execution

- **Two requests at a time.** The HTTP threads (two) parse requests and stream events back; one engine thread takes jobs from a queue in arrival order and runs up to `--batch` (2) at once, each in its own resident session: a prefill chunk alternates with the other request's decode steps (M4 stage 2), and two requests that both decode speculatively verify their rows in one pass (M4 stage 3). A third request waits in the queue ([drafts/M4 §3](./drafts/M4-sessions-and-batches-2026-10-10.md)).
- **Requests are tokenized on the HTTP thread**, so the context check (below) is answered before the job is queued.
- **Cancellation.** A client that disconnects marks its job cancelled; the engine stops at the next emitted token and reports the request as finished with reason `stop`. A job still in the queue when its client leaves runs its prefill and stops at the first token.
- **Limits.** The request body is capped at 64 MB (413 above it); an idle connection is closed after 30 minutes. There is no request timeout: a request runs until its token limit, a stop, the end of the context or a disconnect.
- **State reuse.** A prompt that extends the previous prompt, or a kept prefix checkpoint, resumes from that state instead of prefilling from scratch; `usage.prompt_tokens_details.cached_tokens` says how many tokens were reused.

| Method and path | Answer |
|---|---|

| `GET /v1/models` | `{"object":"list","data":[{"id":NAME,"object":"model","created":…,"owned_by":"ling-engine","root":NAME,"max_model_len":N}]}`. `NAME` is `--served-model-name`; `max_model_len` is `--max-context`. Mightling's launcher reads both. |
| `GET /metrics` | Prometheus text (`text/plain; version=0.0.4`): counters under SGLang's names, so the replay harness reads them unchanged (§6). |

| anything else | `404` with the error shape of §5, type `not_found`. |

## 3. Chat completions and completions

**Request fields** (`parse_request`). Unknown fields are ignored without error.

| Field | Default | Notes |
|---|---|---|
| `messages` (chat) | required | Rendered through the checkpoint's chat template with production's two patches ([docs/V0.md](../docs/V0.md)). Tool messages whose content is a list of text parts are joined; a trailing assistant message is continued. An assistant tool call whose `arguments` string is not a JSON object (cut off by a client, or returned by another server) is rendered verbatim where the parameter blocks would go, the owner's decision of 2026-10-10 and the one place ling-serve knowingly renders a prompt production would not: production answers 400 "Assistant tool call function.arguments must be valid JSON.", clients replay history unchanged and Codex ends the turn on a 400, so the conversation must go on; ling-serve's own parser never emits such arguments, so only histories from other servers reach this path. |
| `prompt` (completions) | required | A string, a one-string list, or a list of token ids. Anything else is a 400. |
| `stream` | `false` | Server-sent events when true. |
| `stream_options.include_usage` | `false` | Streamed: a final chunk with empty `choices` and the `usage` object before `[DONE]`. |
| `max_completion_tokens`, else `max_tokens` | the rest of the context | The generation limit, clipped to what the context has left. |
| `temperature` | `1.0` | 0 is greedy. The defaults are the checkpoint's `generation_config`, as in production. |
| `top_p`, `top_k`, `min_p` | `0.95`, `20`, `0` | |
| `presence_penalty`, `repetition_penalty` | `0`, `1.0` | Set to anything else, the request decodes **plainly**: the drafter is not used, because the penalties change the verify distribution. |
| `seed` | random | An integer seeds the sampler. |
| `stop` | none | A string or a list of strings. Output is held back to a character boundary until a stop can no longer match, so a stop string never leaks in part. |
| `tools`, `tool_choice` (chat) | none, `auto` | `tools` are passed to the template in canonical form (`type`, `function{name, description, parameters, strict}`, `defer_loading`). `tool_choice: "none"` drops them; a named function keeps only that tool; `"required"` is **not enforced**. A tool of any other `type` (a Responses `custom` tool sent here) is dropped: this route offers `function` tools only, as vLLM does. |
| `chat_template_kwargs.enable_thinking`, or top-level `enable_thinking` | template default (on) | Thinking on or off; off, no reasoning is split from the output. |
| `chat_template_kwargs.preserve_thinking`, or top-level | template default | Keeps earlier turns' reasoning in the rendered prompt. |
| `chat_template_kwargs.reasoning_effort`, or top-level `reasoning_effort` | template default (`medium`) | Mapped as production's patched template maps it (`max`/`high` to xhigh, `minimal` to low). `none` switches thinking off, as `reasoning.effort: "none"` does on `/v1/responses` (unless `enable_thinking` is set explicitly). |
| `logprobs` (chat) | `false` | A boolean (anything else is a 400). True: every produced token's log-probability comes back under `choices[0].logprobs` (below). |
| `top_logprobs` (chat) | `0` | An integer 0 to 20: how many of the most likely tokens are listed per produced token. Out of range, or set above 0 without `logprobs: true`, is a 400 (vLLM's rules). |
| `logprobs` (completions) | none | An integer 0 to 20 (null or absent: none; out of range is a 400): the produced tokens' log-probabilities and that many most likely tokens per position, under `choices[0].logprobs`. `true` is read as 0. |

**Ignored without error, by design until built** ([BACKLOG §19.11](./DREAMFERENCE_LING_ENGINE_BACKLOG.md)): `n` (always one choice), `response_format`, `parallel_tool_calls`, `tool_choice: "required"`.

**Logprobs** (built 2026-10-10, vLLM's shapes and its default `raw_logprobs` mode). The value is the log-softmax of the model's raw logits at the position, computed on the host from the row the token was chosen from, before temperature, top-k, top-p, min-p or penalties: what the model believed, not what the sampler drew from. **One entry per produced token, the thinking span included**: with thinking on, the tokens of the reasoning, `</think>` and the blank line after it have entries like any other, so on chat the `content` list is per token regardless of whether its text went to `reasoning_content` or `content`, and its length is `completion_tokens` (the end-of-turn token is never produced and has no entry; a token that completes a stop string has one though its text is cut). Per entry `token` is the token's text, `bytes` the list of its exact bytes (a character the model split across two tokens shows as U+FFFD in each `token`, and whole in the two `bytes` lists), `logprob` the value (always `<= 0`). The most likely tokens are ranked by logit, ties to the lower id, so at temperature 0 the chosen token is the first listed with the same `logprob`. **Speculation stays on**: the verify pass computes every row's logits (bit for bit what plain decoding gives, [SPECULATION](./DREAMFERENCE_LING_ENGINE_SPECULATION.md)), and for a request that asks for logprobs the engine copies the accepted rows (`accepted + 1` rows of `vocab` floats per step) to the host, checks them whole for NaN and inf (the verify checks each row's top K only; a NaN row ends the request as §5 says) and takes the log-softmax of each. A request without logprobs copies nothing and computes nothing extra.

**Unstreamed answer.** `{"id":"chatcmpl-…"|"cmpl-…","object":"chat.completion"|"text_completion","created":…,"model":NAME,"choices":[{"index":0,"message":{…}|"text":…,"finish_reason":…}],"usage":{…}}`. The chat message carries `role`, `content` (null when the answer is tool calls only), `reasoning_content` when thinking produced any, and `tool_calls` (`id` `call_…`, `type: "function"`, `function{name, arguments}` with `arguments` as JSON text). `finish_reason` is `stop` (the end-of-turn token or a stop string), `length` (the token limit or the end of the context), `tool_calls` (stopped with at least one call), or `repetition` (the output ended in a loop: the repetition stop rule, §9). `usage` has `prompt_tokens`, `completion_tokens`, `total_tokens` and `prompt_tokens_details.cached_tokens`; on chat completions also `completion_tokens_details.reasoning_tokens`, the thinking span's share of `completion_tokens`, counted by the engine from the token ids as they are produced (up to and including `</think>` and the blank line after it; every token when the answer was cut inside the span; 0 with thinking off), so the count is exact under speculation and never exceeds `completion_tokens`. With logprobs asked for, the choice carries `logprobs`: on chat `{"content":[{"token":…,"logprob":…,"bytes":[…],"top_logprobs":[{"token":…,"logprob":…,"bytes":[…]},…]},…]}`, one element per produced token, `top_logprobs` holding `top_logprobs` entries: the chosen token first, then the most likely others by rank (as vLLM lists them: a chosen token outside the top k displaces the k-th; empty when `top_logprobs` is 0); on completions `{"tokens":[…],"token_logprobs":[…],"top_logprobs":[{token: logprob,…},…],"text_offset":[…]}`, the lists one element per produced token, each `top_logprobs` map holding the chosen token and the `logprobs` most likely ones (so `logprobs` or `logprobs + 1` keys, as vLLM gives them), `text_offset` the position of each token's text in `text`, in characters (a byte that does not continue a character starts one, so a character split across tokens counts once). Without logprobs the key is absent.

**Streamed answer.** `Content-Type: text/event-stream`; each event is `data: <chunk>\n\n`; the stream ends with `data: [DONE]\n\n`. Chat chunks are `chat.completion.chunk` objects with one `choices[0].delta`: the first carries `role`, then `reasoning_content` and `content` as they arrive, and `tool_calls` entries (each with `index`, `id`, `type` and the whole `function` at once: a call is emitted when its closing marker has been parsed, not token by token). Completions chunks are `text_completion` objects with `choices[0].text`. A final chunk with an empty delta carries `finish_reason`; then, if asked, the usage chunk; then `[DONE]`. With logprobs asked for, each chunk's `choices[0].logprobs` has the unstreamed shape for the tokens produced since the previous chunk (`text_offset` counted over the whole output); because the decoder and the parser can hold a token's text back (a split character, a possible marker), a token's entry can arrive a chunk before its text, and entries still pending at the end ride on the final chunk, so the chunks' lists concatenate to exactly the unstreamed list. While nothing has been produced yet (the request waits in the worker's queue, or its prompt is in prefill) the stream carries the SSE comment line `: keep-alive` every `--keepalive-seconds` (15 by default, 0 switches it off; [CLI §1](./DREAMFERENCE_LING_ENGINE_CLI.md)), so a client with an idle timeout keeps the stream through a long prefill or a queue of requests ahead. A comment line is ignored by every conforming SSE parser (read in the OpenAI Python SDK and in `eventsource-stream`, which Codex uses; the AI SDK's parser, which Cline uses, is assumed to follow the specification). The keep-alives stop at the first token (or at the error, or the end, if nothing was produced) and are never sent on an unstreamed request.

**Tool calls are parsed from the model's text** (`OutputParser`): a `<tool_call>` marker starts a call only when `<function=` follows and names a function the request offered, and never inside a Markdown code fence, so an example in a fence, the template's placeholder name or a marker quoted in prose stays text ([VALIDATION §18](./DREAMFERENCE_LING_ENGINE_VALIDATION.md)). Arguments are rendered to JSON with the parameter types the tool schema declares.

## 4. The Responses API

`POST /v1/responses` is converted to a chat request the way SGLang converts it (`parse_responses_request`), then runs as §3 with thinking on unless switched off:

- `instructions`, and `developer` messages in `input`, become one leading system message; `input` is a string or a list of items (`message`, `function_call`, `function_call_output`, `custom_tool_call`, `custom_tool_call_output`, `reasoning`); function calls and their outputs become assistant tool calls and tool messages; reasoning items become `reasoning_content`; `function` and `custom` tools reach the template, every other tool type is dropped; `tool_choice: "none"` drops them all.
- **Custom (freeform) tools** (`{type: "custom", name, description, format}`, Codex's `apply_patch` for some model families): the model has no freeform tool format and production SGLang drops `type: custom` tools (read from its source on 2026-10-09 and seen live on 2026-10-10: the same Code Mode `ling exec` carried the custom `exec` tool in every request and the model never called it in eleven turns against production, while against ling-serve it called it three times in seven turns and the task completed), so the rendering is ling-engine's own and the only one in use (the owner's choice, 2026-10-10). A custom tool is offered as a function with the one string parameter `input` (its `description` rendered with the grammar from `format` appended to it as prose, the grammar not enforced), and a call to it comes back as a `custom_tool_call` item whose `input` is that parameter's text (failing that, the single string parameter the model used instead; failing that, the arguments text itself). A replayed `custom_tool_call` renders as that one-parameter call, so the turn renders as the model wrote it; a `custom_tool_call_output` is a tool message like a `function_call_output`. The grammar is rendered because without it the model answered a unified diff where apply_patch's syntax was wanted (2026-10-10); it is not enforced, so the dialect stays the model's choice (`test_responses_custom_tool_call_stream` checks the item, not the dialect; what the model wrote is in `reports/api-compat-checklist.md`). Constraining the output to the grammar is the follow-up if the agent still needs it ([BACKLOG §19.13](./DREAMFERENCE_LING_ENGINE_BACKLOG.md)). On chat completions, the vLLM-compatible route, a `type: custom` tool is dropped: only `function` tools reach the template there.
- `max_output_tokens` is the limit; `stream`, the sampling fields, `stop`, `seed` and `chat_template_kwargs` pass through; `reasoning.effort` becomes the template's effort, except `none`, which switches thinking off.
- A request body that is not an object, or has no `input`, is a 400.
- **Accepted and ignored**, by the owner's decision (2026-10-10): the fields Codex sends on every turn that change nothing here are parsed without error and dropped, never refused, because Codex treats a 400 as the end of the turn. They are `parallel_tool_calls` (calls are emitted as the model writes them, in order), `store`, `include` (`reasoning.encrypted_content`: the reasoning item carries its text instead), `client_metadata`, `service_tier`, `reasoning.summary` (no `reasoning_summary_text.*` events; Codex tolerates their absence), `text.verbosity`, `metadata`, `user`, `truncation`, and `tool_choice: "required"` (not enforced, [BACKLOG §19.11](./DREAMFERENCE_LING_ENGINE_BACKLOG.md)). `text.format` is in the same list until structured output exists. `prompt_cache_key` (Codex's thread id) is used since M4 stage 1 ([BACKLOG §19.8](./DREAMFERENCE_LING_ENGINE_BACKLOG.md), [drafts/M4 §1](./drafts/M4-sessions-and-batches-2026-10-10.md)): the session key, where the engine looks for the request's resident session first (a hint: the token prefix decides what is reused) and what protects the session from eviction for `--session-protect-seconds` after its last request; the chat and completions routes accept it too.

**Streamed** (what Mightling's agent parses), each event `event: <type>\ndata: <json>\n\n` with a `sequence_number`: `response.created` (status `in_progress`); then, while no token has been produced yet (the request waits in the worker's queue, or its prompt is in prefill), a `response.in_progress` event every `--keepalive-seconds` (15 by default; [CLI §1](./DREAMFERENCE_LING_ENGINE_CLI.md)) carrying the same response object, status `in_progress`, numbered like any event (Codex lists the kind among those it ignores), so a client with an idle timeout keeps the stream; the keep-alives stop at the first token (as on the chat route, §3), so none follows the first output item; then per output item `response.output_item.added`, its deltas (`response.reasoning_text.delta` for a `reasoning` item, `response.output_text.delta` for a `message` item), `response.output_item.done`; a `function_call` item is added and done at once with `name`, `arguments`, `call_id`; a `custom_tool_call` item is added with `name`, `call_id` and `input` present but empty (Codex parses the item only with `input` present), then one `response.custom_tool_call_input.delta` with the whole input, keyed by `item_id` and `call_id` as Codex reads it, then `response.custom_tool_call_input.done`, then `response.output_item.done` with the full item; then `response.completed` with the whole response object. **A response cut at `max_output_tokens` still ends with `response.completed`**, status `incomplete` and `incomplete_details.reason: "max_output_tokens"`, because the agent treats `response.incomplete` as a failed turn and discards what was written. **A repetition stop (§9) is the exception:** it ends with `response.incomplete`, status `incomplete`, `incomplete_details.reason: "repetition"` and `stop_reason: "repetition"`, after every reasoning and text delta up to the loop's last token, so the `ling` launcher's loop guard can rebuild the turn and nudge or end it; `--repetition-report completed` makes it a `response.completed` with status `completed` and `stop_reason: "repetition"` instead, for Responses clients without that guard (plain Codex 0.158 retries any `response.incomplete` up to five times, which would run the loop again). `usage` has `input_tokens`, `input_tokens_details.cached_tokens`, `output_tokens`, `output_tokens_details.reasoning_tokens` (the thinking span's share, counted as on the chat route, §3; Codex displays and budgets on it) and `total_tokens`.

**Unstreamed**: the same response object, `200`.

## 5. Errors

The error shape is OpenAI's: `{"error":{"message":…,"type":…,"code":…}}`, `code` present when there is one.

| Case | Answer |
|---|---|
| Body not JSON, not an object, missing `messages`/`prompt`/`input`, a bad `prompt` | `400`, type `invalid_request_error`. |
| Prompt longer than the context | **Before any header is sent**: `400`, type `invalid_request_error`, code `context_length_exceeded`, a message in the form the clients' libraries recognise ("maximum context length is …"). This is the one error the agents compact on; Codex retries a `server_error` instead. |
| The same, found while a stream is already open | Chat and completions: an error object as a `data:` event, then a chunk whose `finish_reason` is `error`, then `[DONE]`, so no stream is left unterminated. Responses: `response.failed` with `error.code` `context_length_exceeded`, then the stream ends. |
| Logits not finite (NaN or inf) during a request | The request **ends with an error** rather than sampling garbage (sampled anyway they gave `!` forever, or a uniform draw streamed as a healthy answer: [VALIDATION §18](./DREAMFERENCE_LING_ENGINE_VALIDATION.md)): `500`, type `server_error`, or the streamed forms above; counted in `ling:nonfinite_logits_total`. |
| Any other exception in the engine | `500`, type `server_error`, or the streamed forms. |
| Body over 64 MB | `413`, type `invalid_request_error`. |
| Unknown route | `404`, type `not_found`. |

the harness divides it by its per-task budget, 49,152 by default, so it admits two tasks, [SESSIONS §11](./DREAMFERENCE_LING_ENGINE_SESSIONS.md), [drafts/M4 §1](./drafts/M4-sessions-and-batches-2026-10-10.md)); and the session pool's `ling:sessions` (slots), `ling:sessions_resident` (slots holding a session), `ling:session_evictions_total` and `ling:session_protect_seconds`; and the scheduler's `ling:batch` (requests that run at once), `ling:prefill_chunk_contended` (the prefill chunk beside a decode) and `ling:prefill_chunks_interleaved_total` (prefill chunks run between another request's steps; a batched step's draft, verify and commit seconds are the batch's wall times, counted for each sequence in it, M4 stage 3), and the shadow-mode counters (`shadow_*`) that measure the lookup source without using it ([SPECULATION §10](./DREAMFERENCE_LING_ENGINE_SPECULATION.md)).

## 7. What a client should not expect yet

Two requests at a time, their decode steps batched (one verify pass over both requests' rows since M4 stage 3; a prefill chunk still alternates with the other request's steps; a third waits); no `n > 1`, no structured output (`response_format`, `text.format`), no enforced `tool_choice: "required"`; images answered as text: there is no vision encoder, so an image part (`image_url` on chat completions, `input_image` on `/v1/responses`) renders as the placeholder `[image]` in the message's content, the text parts around it as they are, and the turn goes on instead of ending on a 400 (since 2026-10-10; video is still refused); the chat template is compiled in (the checkpoint's with production's patches), not read from a file at launch. Each is in [BACKLOG §19](./DREAMFERENCE_LING_ENGINE_BACKLOG.md) with its rank; the request fields accepted and ignored on `/v1/responses` are listed in §4. **The goal (the owner's decision, 2026-10-10) is the complete Codex Responses API on `/v1/responses`, with the chat and completions routes kept as the vLLM-compatible surface for the other clients, and no protocol of ling-engine's own** ([BACKLOG §19.15](./DREAMFERENCE_LING_ENGINE_BACKLOG.md)); the gaps against the pinned Codex source are listed there; custom tools landed on 2026-10-10 (§4); `reasoning_tokens` is next. The regression tests in `tests/server/test_regressions.py` state, per upstream bug class, whether the server handles or refuses the case.

## 8. Speed-only extensions

*Decided 2026-10-12 (BACKLOG §19 item 15, relaxed): the API matches Codex's Responses API and the vLLM-compatible routes, plus optional arguments that only make a request faster.* They travel in one object, `ling`, on every route. A request without it is served exactly as before; with it, the output (tokens, logprobs, usage) is identical, only the speed may change, because extensions feed what speculation proposes, never what it accepts. Unknown keys inside `ling` are ignored (a newer client against an older server degrades to no speed-up); a malformed value of a known key is a 400 naming the key. Clients send it only to a server whose `/v1/models` says `owned_by: ling-engine`. Keys: none built yet. Planned: `lookup_corpus` (BACKLOG §19.20: the repository's identifiers and n-grams, or the hash of a corpus uploaded once per session).

## 9. The repetition stop rule

*The owner's decision of 2026-10-20.* A model caught in a loop writes the same block until the token limit, minutes of a GPU for nothing. ling-serve ends such a request on the CPU, at no GPU cost, from the tokens each step accepts: when the output, **reasoning included**, ends in a block of `min_pattern_size` .. `max_pattern_size` tokens repeated `min_count` times back to back, or in one token repeated `max_run` times. The output up to and including the token that completed the loop is sent unchanged (what was produced is what greedy or sampled decoding produced; the rule only decides where it stops), and the request ends with `finish_reason: "repetition"` on chat completions and completions, and on `/v1/responses` as §4 describes. Each stop counts in `ling:repetition_stops_total`, and the request's log line says `repetition`.

The test on the output's tail is vLLM's (`RepetitionDetectionParams`, `check_sequence_repetition` in `v1/core/sched/utils.py`; `api_tests` compares the two at every token of 48,000 outputs), kept incrementally: one comparison per period and token. `max_run` is ling-engine's own, for one token repeated, which the defaults leave out of the block test (a run of a short token is common in code; a run of 64 is not).

**Per request**, the vLLM-shaped field `repetition_detection` on every route: an object with any of `max_pattern_size`, `min_pattern_size`, `min_count` (as vLLM's) and `max_run`, each field it leaves out taking the server's value; `false` switches the rule off for the request (`true` or null: the server's rule). Invalid values (as vLLM validates: sizes ≥ 0, `min_pattern_size` ≤ `max_pattern_size`, `min_count` ≥ 2 when the block test is on; `max_run` 0 or ≥ 2) are a `400`. **Per server**, `--repetition-detection P,p,R,K` (`max_pattern_size`, `min_pattern_size`, `min_count`, `max_run`) or `off`, and `--repetition-report incomplete|completed` ([CLI §1](./DREAMFERENCE_LING_ENGINE_CLI.md)).

**The default, on: blocks of 2 to 256 tokens repeated 12 times, and runs of 64.** Measured on outputs this model wrote (2026-10-20, `bench/repetition/rep_stats.py`): the production SWE-bench rollouts (M0's Codex traces: 43,832 responses, 5.9 million tokens of messages and tool-call arguments; the rollouts keep no reasoning text) and the step dumps of bench/agentlong (`LING_DUMP_STEPS`: six turns greedy and the sixteen at seed 1013, 6,964 tokens, reasoning included). Their worst cases: a 2-token block repeated 7 times, blocks of 3 to 7 tokens 4 times, 8 and 12 tokens 3 times, every longer block (to 512) twice, and a run of 14 tokens. The default leaves a margin of 5 repeats over the worst short block and stops a 40-token paragraph looping at its twelfth copy.
